# Стенд Service Desk для интеграции студентов

Стенд предоставляет готовую службу поддержки и единый вход через Keycloak. Студенты разрабатывают свой сервис в отдельном репозитории: подключают авторизацию, принимают уведомления об обращениях, назначают исполнителей и меняют статусы через API.

В составе две системы:

- **Identity** — Keycloak с LDAP: пользователи, пароли, роли и вход через OpenID Connect.
- **Service Desk** — портал Artsofte, API обращений и отправка webhook.

## Подключение к готовому стенду

Для интеграции достаточно адресов сервисов, выданных учётных записей и ключа проверки webhook. Доступ к исходникам стенда не требуется. Студенты администрируют выданный стенд через консоль Keycloak и API настроек.

Три инструкции описывают работу по порядку:

1. [Keycloak: пользователи и роли](docs/students/01-keycloak-and-roles.md) — создание учёток, группы и права собственного сервиса.
2. [OpenID Connect и форма входа](docs/students/02-openid-connect.md) — подключение проекта, localhost, callback, проверка токена и выход.
3. [Интеграция с Service Desk](docs/students/03-service-desk.md) — proxy, webhook, исполнители, переписка и статусы.

Локальное приложение студентов может работать с удалённым стендом. Запросы к Service Desk проходят через их backend или dev-proxy. Для получения webhook на localhost нужен публичный HTTPS-туннель. После переноса приложения на стенд команды в Keycloak добавляются новые адреса возврата, а URL получателя обновляется через API настроек.

## Как проходит обращение

1. Заявитель создаёт обращение в портале Artsofte. Оно назначается активному руководителю своей службы поддержки.
2. Service Desk сохраняет обращение, историю и событие `jira:issue_created` одной транзакцией. Настроенный получатель получает подписанный webhook.
3. Сервис студентов сохраняет событие и показывает обращение сотруднику поддержки. Правила распределения и интерфейс назначения реализуются в этом сервисе.
4. Назначение, комментарий и смена статуса создают `jira:issue_updated`.
5. Заявитель закрывает своё обращение. Статус становится «Закрыта», исполнитель снимается; оба изменения входят в одно событие обновления.

В портале доступны создание, список со статусами, карточка и переписка. Исполнитель отображается только для чтения. В списке используется виртуальная прокрутка с автоматической подгрузкой, без переключения страниц.

## Запуск своего стенда

Нужны Docker Engine с Compose v2 и Node.js `22.23.1` из `.nvmrc`. Команды выполняются из корня репозитория:

```sh
node tools/setup-env.mjs
node tools/bootstrap.mjs --mode docker
node tools/bootstrap.mjs --mode docker --apply
```

`setup-env` создаёт `.env` с локальными секретами. Если файл уже существует, вместо первой команды используется:

```sh
node tools/setup-env.mjs --extend
```

Она добавляет недостающие ключи, сохраняя действующие значения. Bootstrap без `--apply` показывает план. С `--apply` он запускает инфраструктуру, применяет миграции, готовит начальные данные и настраивает Identity.

| Раздел              | Адрес после локального запуска          |
| ------------------- | --------------------------------------- |
| Создание обращения  | <http://localhost:8080/>                |
| Обращения и статусы | <http://localhost:8080/requests>        |
| Swagger             | <http://localhost:8080/docs/>           |
| OpenAPI             | <http://localhost:8080/docs/json>       |
| Консоль Keycloak    | <http://localhost:8081/admin/>          |
| Issuer              | `http://localhost:8081/realms/training` |

Контур содержит пять сервисов: `postgres`, `ldap`, `identity`, `migrate`, `service-desk`. `migrate` выполняет миграции и завершается с кодом `0`; остальные работают постоянно. API и Angular-портал собраны в одном контейнере.

Используется один PostgreSQL и одна БД `training`: таблицы Service Desk находятся в `public`, таблицы Keycloak — в `identity`. Пароли пользователей хранятся в LDAP.

Статусы, журналы и остановка:

```sh
docker compose ps --all
docker compose logs --tail=100 service-desk identity
docker compose down
```

Остановка без `--volumes` сохраняет данные. Порты, тома и перенос прежней БД Identity описаны в [инструкции Docker](docs/docker.md). `/health` проверяет работу процесса; проверка входа и доставки уведомлений выполняется отдельно.

## Начальные учётные записи

| Логин           | Назначение                                         | Переменная пароля в `.env` |
| --------------- | -------------------------------------------------- | -------------------------- |
| `alice`         | Алиса Иванова, заявитель                           | `LDAP_ALICE_PASSWORD`      |
| `support`       | Сергей Петров, сотрудник поддержки                 | `LDAP_SUPPORT_PASSWORD`    |
| `support-lead`  | Руководитель поддержки, первоначальный исполнитель | `SUPPORT_LEAD_PASSWORD`    |
| `desk-admin`    | Администратор службы поддержки                     | `DESK_ADMIN_PASSWORD`      |
| `denied`        | Проверка отказа в доступе                          | `LDAP_DENIED_PASSWORD`     |
| `administrator` | Администратор Keycloak в realm `master`            | `IDENTITY_ADMIN_PASSWORD`  |

Пароли передаются команде отдельно, их значений в репозитории нет. Администратор Keycloak управляет пользователями и клиентами. Администратор службы поддержки меняет настройки приложения — один доступ не выдаёт другой автоматически.

Роли API находятся в клиенте `service-desk`: `customer`, `support`, `support-lead`, `admin`. Руководитель наследует права поддержки. Для новых обращений нужен ровно один активный руководитель своего Service Desk; при отсутствии или нескольких кандидатах создание возвращает `503` без записи обращения. Текущую учётку и эффективную роль возвращает `GET /api/me`.

## API и уведомления

Поддерживаются 14 операций: выбранное подмножество Jira Service Management Data Center 10.3 и собственные методы учётной записи и настроек. Пути, примеры и отличия от Jira описаны в [контракте API](docs/api-compatibility.md).

Запросы выполняются с access token Identity. Для API нужны audience `service-desk`, роль из `resource_access.service-desk.roles` и корректный `team_slug`. Сервер проверяет подпись, срок токена и доступ к службе поддержки. Пароль вводится на странице Identity.

Webhook подписывается HMAC-SHA256. Получатель проверяет подпись по исходным байтам тела и исключает повторы по `X-Training-Event-Id`. Порядок доставки не гарантируется. Подробности и пример обработчика — в [инструкции интеграции](docs/students/03-service-desk.md).

## Настройки через JSON

`config/backend.json` — шаблон. Рабочий документ хранится по пути `SETTINGS_FILE` и создаётся только при отсутствии файла. В Docker для него используется постоянный том.

| Метод                 | Действие                  |
| --------------------- | ------------------------- |
| `GET /api/settings`   | Получить весь документ    |
| `PUT /api/settings`   | Заменить документ целиком |
| `PATCH /api/settings` | Изменить отдельные поля   |

Методы доступны администратору службы поддержки. Адреса уведомлений применяются на следующем цикле обработки без перезапуска; остальные параметры — после перезапуска. Заголовок `X-Restart-Required` сообщает о его необходимости. `ETag` и `If-Match` защищают от потери параллельных правок.

JSON содержит разрешённые имена переменных окружения, а секреты остаются в ENV. Формат и примеры — в [настройках](docs/settings.md), управление доступом — в [руководстве по пользователям и ролям](docs/students/01-keycloak-and-roles.md).

## Разработка стенда

Проект использует pnpm и Nx. Сервер написан на Fastify и TypeScript с Drizzle ORM; портал — на Angular с общей библиотекой PrimeNG/Aura.

```sh
corepack enable
pnpm install --frozen-lockfile
node tools/bootstrap.mjs --mode dev --apply
pnpm start
```

| Путь                    | Содержимое                           |
| ----------------------- | ------------------------------------ |
| `apps/identity`         | Keycloak, тема входа и образ LDAP    |
| `apps/service-desk/src` | Сервер: слои `api → logic → dal`     |
| `apps/service-desk/ui`  | Портал заявителя                     |
| `libs/ui`               | Готовые контролы и общая тема UI     |
| `libs/theme`            | SCSS-токены, стили Identity и шрифты |
| `infra`                 | Compose и подготовка инфраструктуры  |

SQL-миграции находятся в `apps/service-desk/src/dal/migrations`, Dockerfiles — рядом с приложениями. Применённые миграции не редактируются; существующие ENV и тома сохраняются при обновлении.

Архитектура описана в [обзоре](docs/architecture/README.md), проверки — в [матрице](docs/agents/verification.md), правила работы агентов — в [AGENTS.md](AGENTS.md).

## Границы реализации

Стенд воспроизводит выбранные методы Jira Data Center 10.3. Полной совместимости с Jira и Cloud API нет. Тип `10001` моделирует замену оборудования; формы `183` и `194` описаны отдельно. Вложения, участники, SLA, 1С, массовая генерация и автоматическое создание раздела Service Desk при добавлении пользователя Identity не реализованы.

Локальный запуск использует собственные данные и не подключается к корпоративным сервисам. Для размещения на домене отдельно настраиваются HTTPS, публичные адреса Identity/API, защита LDAP, секреты и резервное копирование. Локальная команда запуска сама не публикует стенд на VPS.
