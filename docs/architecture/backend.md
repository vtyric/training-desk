# Сервер: устройство и правила изменений

## Граница проекта

Сервер предоставляет внешние системы для интеграции студентов. Он хранит обращения, отдаёт выбранное подмножество Jira Service Management API и отправляет события. Приложение студентов находится в отдельном репозитории. Angular-портал встроен в `apps/service-desk/ui`, API — в `apps/service-desk/src`; оба входят в один Nx-проект `service-desk`. Пароль проверяет самостоятельный Identity.

Корпоративные Jira/LDAP/ADFS не используются во время работы. Наблюдавшийся корпоративный вход был OIDC через ADFS; наш отдельный Identity реализован на Keycloak с учебным LDAP. Service Desk — сервер API с проверкой JWT без прямого LDAP bind, формы входа, callback и локальных сессий. Не копировать корпоративные секреты, пользовательские данные и конфигурацию в seed, примеры или тесты; не выполнять записи в корпоративные системы.

Контракт и отличия от Jira описаны в [api-compatibility.md](../api-compatibility.md). Управление Service Desk — в [administration.md](../administration.md), установка — в [docker.md](../docker.md). Эти документы не заменять повторяющимися списками API здесь.

## Куда вносить изменение

| Место                                       | Ответственность                                                           |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| `apps/service-desk/src/api/routes.ts`       | HTTP-методы, JSON Schema, извлечение параметров и principal, коды ответов |
| `apps/service-desk/src/logic/requests.ts`   | Создание, видимость, переходы, комментарии, транзакционные сценарии       |
| `apps/service-desk/src/logic/catalog.ts`    | Поля типов 183/194, значения полей и переходы статусов                    |
| `apps/service-desk/src/logic/presenters.ts` | Представления issue/request, даты, пагинация                              |
| `apps/service-desk/src/dal/`                | Drizzle-схема, репозитории, PostgreSQL, миграции и seed                   |
| `libs/auth/{logic,dal}` и entrypoint        | Проверка JWT/JWKS и роли Identity                                         |
| `libs/webhooks/{logic,dal}`                 | Worker, HTTP-транспорт и состояние доставок                               |

Направление зависимостей — `api → logic → dal`. В API нет запросов к БД; DAL не импортирует входящие HTTP-обработчики или бизнес-логику; logic не импортирует Fastify. Параметры БД, principal и DTO передавать явно; не скрывать доступ к хранилищу в глобальных переменных.

ESLint проверяет эти ограничения. Исключения композиции: `app.ts`, `runtime.ts`, `main.ts`, а также `libs/**/index.ts` и тесты. Наличие исключения позволяет собирать зависимости, а не переносить туда прикладные сценарии. Новый функциональный модуль также разделять на `api`, `logic`, `dal`.

Исходящий HTTPS-транспорт и DNS-проверка назначения находятся в `libs/webhooks/dal/transport.ts` и `libs/webhooks/dal/destination.ts`. Логика worker вызывает эти адаптеры; доступ к внешней сети не смешивается с HTTP-контроллерами или правилами доставки.

## Сборка приложения

`main.ts` вызывает `buildRuntimeApp()` и открывает порт. `runtime.ts` собирает проверку JWT Identity, Swagger и доставку событий; дополнительно раздаётся собранный портал при `ui.enabled` и `STATIC_DIR`. Входом в браузере управляет `keycloak-js`; сервер не создаёт сессию пользователя. `runtime.ts` передаёт зависимости в `buildApp()` из `app.ts`:

- `configureApp` регистрирует плагины до основных маршрутов;
- JWT-адаптер проверяет access token и адаптирует проверенные claims к principal;
- `assigneeDirectory` читает актуальные роли сотрудников из Identity;
- `trainingDb` используется точкой композиции для поиска активного раздела Service Desk.

Проверка адресов уведомлений находится в `runtime.ts` и передаётся в модуль настроек. При внешнем запуске публичные API и issuer требуют HTTPS; локальные HTTP-исключения JWT-транспорта отключены.

`DomainError` и ожидаемый `AuthError` отображаются в контролируемый HTTP-ответ. Детали неожиданных SQL/OIDC ошибок клиенту не выдаются. Неизвестные операции возвращают 404, некорректные поля — 400. Не включать автоматическое удаление неизвестных полей JSON Schema: ошибочное поле должно обнаруживаться вызывающим сервисом.

## Хранение данных

Основная Drizzle-схема: `apps/service-desk/src/dal/schema.ts`.

| Таблица                 | Назначение                                                         |
| ----------------------- | ------------------------------------------------------------------ |
| `teams`                 | Slug команды, имя, активность                                      |
| `training_users`        | Исторические seed-записи; API не использует их как источник ролей  |
| `api_tokens`            | Хеши токенов, роль, владелец, отзыв и необязательный срок действия |
| `issues`                | Состояние обращения, поля формы, автор, исполнитель, `version`     |
| `comments`              | Публичные ответы и внутренние заметки                              |
| `issue_history`         | Автор, время и данные изменения                                    |
| `webhook_subscriptions` | Команда, адрес, секрет и момент регистрации подписки               |
| `webhook_outbox`        | Неизменяемое тело события после изменения обращения                |
| `training_migrations`   | Реестр SQL-миграций и их SHA-256                                   |
| `webhook_deliveries`    | Попытки, lease и результат доставки пары событие/подписка          |

Первые восемь таблиц описаны общей схемой. `training_migrations` создаётся runner миграций. Доставки создаются отдельным DAL-адаптером через `CREATE TABLE IF NOT EXISTS` при инициализации runtime; они не включены в общий Drizzle snapshot. Прежние таблицы browser-сессий/OIDC-транзакций могли сохраниться в старой БД, но текущим сервером API не используются. Это существующее ограничение: изменение их структуры требует явной миграции, простого редактирования `CREATE TABLE IF NOT EXISTS` недостаточно.

Запросы предметного DAL выполняются через Drizzle; специальные SQL для bootstrap, advisory lock, leases и `SKIP LOCKED` находятся в DAL. Не строить SQL конкатенацией пользовательских значений. Новые фильтры добавлять как параметризованные выражения.

## Инварианты записи

Пример создания:

```text
POST request
  → API проверяет JSON и авторизацию
  → logic проверяет тип, обязательность и значения полей
  → transaction: issue + history + outbox
  → commit
  → 201 с request DTO
  → отдельный worker доставляет событие
```

Внешний HTTP-запрос webhook не выполняется внутри транзакции и не отменяет создание обращения при ошибке доставки.

Переход и комментарий используют `issues.version`: обновление выполняется по ID, команде и прежней версии, затем атомарно увеличивает версию. Ноль обновлённых строк означает конфликт и ответ 409; история/комментарий/событие при этом откатываются. Это серверная оптимистическая проверка конкурентных операций, не клиентский `If-Match` или `expectedVersion` контракт.

Сохранять следующие правила:

- Команда берётся из principal, а не из тела обращения. Чтение/изменение обращения другой команды возвращает 404.
- Заявитель видит свои обращения; сотрудник поддержки — обращения своего Service Desk.
- Внутренние комментарии не выдаются customer и их текст не входит в webhook.
- Исполнитель должен быть активным сотрудником поддержки того же Service Desk; его роль проверяется в Identity.
- Переход проверяется в logic заново; нельзя доверять ранее загруженному списку.
- Формирование DTO остаётся в presenter; SQL-строка не служит публичным ответом API.

## Миграции и проверка

Изменить Drizzle schema → `pnpm db:generate` → проверить новый SQL и metadata → `pnpm db:migrate`. Общая baseline — `0000_initial.sql` и `src/dal/migrations/meta`. Применённый SQL не редактировать.

Runner читает `NNNN_name.sql` по порядку, проверяет уникальность номеров, SHA-256 и наличие всех применённых файлов. Он запрещает вставку нового файла перед уже применённым. Обновление выполняется в одной транзакции под advisory lock; текущая реализация подходит только для транзакционного SQL. `CREATE INDEX CONCURRENTLY` в такую миграцию добавлять нельзя без изменения runner.

`seed.ts` создаёт demo только при отсутствии команды; повторный запуск не меняет токены. Изменять существующие учётные данные следует явной административной операцией.

После изменения сервера выполнить TypeScript, ESLint/Prettier для изменённых файлов и соответствующие серверные тесты. `pnpm test` включает сценарии API, сервер API с проверкой JWT, webhook и миграций; для них нужна локальная инфраструктура из инструкции установки. Тест миграций использует отдельную временную БД и удаляет её после проверки.

## Реализовано и отложено

Реализованы исследованные формы 183/194 и отдельный учебный тип замены техники 10001, основной цикл обращения, изоляция API-команд, JWT-проверка самостоятельного Identity, outbox и преподавательские API. Полный перечень совместимости хранится отдельно.

Пока нет GUI преподавателя, сброса/массовой генерации данных, provisioning LDAP каждой команды, вложений/участников и полной схемы Jira. Не описывать эти возможности как существующие и не добавлять корпоративные автоматизации без отдельного согласования объёма.

## Граница Identity

Identity — отдельное приложение `apps/identity` со схемой `identity` в общей БД и LDAP federation с записью. Пользователи/пароли управляются через Keycloak Admin Console; роли `service-desk:заявитель/сотрудник поддержки/администратор` хранятся в Keycloak. Подключение студентов — в [identity.md](../identity.md).

Service Desk не принимает пароль, не обменивает code, не выдаёт cookie и не содержит server auth login/logout/session или OIDC code callback endpoints; `/auth/callback` — маршрут встроенного SDK UI. `libs/auth` проверяет JWT access token через `jose` и публичные JWKS: подпись, issuer, audience `service-desk` и временные ограничения. Из верифицированных claims берутся `preferred_username`, `team_slug` и `resource_access["service-desk"].roles`. LDAP-группы и роли другого OIDC-клиента не дают доступа к API.

Команда определяется по доверенному `team_slug` и должна существовать/быть активной в SQL. Допуск customer/support проверяется на сервере, а роль admin разрешает административные API. Principal не строится из непроверенного декодированного JWT. Для проверки JWT секрет клиента не нужен. Каталог сотрудников использует отдельный серверный client secret с правами чтения.

Статические support/customer bearer поддерживаются отдельно, но default runtime `security.allowLegacyApiTokens=false`. Bootstrap `ADMIN_TOKEN` сохраняется независимо; JWT role admin также разрешает административный API. Они не являются паролями Keycloak и не создают SSO-сессию. Создание API-команды не добавляет автоматически пользователя/роли в Identity.

## JSON settings

`libs/settings/{api,logic,dal}` хранит `SETTINGS_FILE` по схеме `config/backend.json`. Файл — основной источник, секретные значения не хранятся: только фиксированные имена переменных окружения. При отсутствии state копируется шаблон, существующий state не перезаписывается. Подробнее — [settings](../settings.md).

`GET/PUT/PATCH /api/settings` доступны только администратору службы поддержки: полный JSON без обёртки, ответ 200. Изменённые адреса уведомлений worker применяет на следующем цикле; остальные параметры требуют перезапуска, о чём сообщает X-Restart-Required. API не делает скрытую двойную запись JSON/SQL.

JSON сохраняется атомарным переименованием с fsync и правами 0600. Записи упорядочены блокировкой внутри процесса; межпроцессной блокировки нет. `ETag`/необязательный `If-Match` защищают от устаревшей revision (`409`). Полный документ доступен администратору службы поддержки; произвольные ссылки на переменные окружения запрещены.

Настройки: только GET/PUT/PATCH /api/settings, полный SettingsDocument admin-only. Прежние административные REST команд/токенов/подписок удалены; начальные данные и изоляционные тестовые данные готовятся через DAL.
