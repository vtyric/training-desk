# Сервер Service Desk

Service Desk хранит обращения и предоставляет выбранные методы Jira Data Center 10.3. Angular-портал находится в том же Nx-проекте, что API. Приложение студентов обращается к серверу по HTTP и получает webhook.

Контракт методов описан в [совместимости API](../api-compatibility.md), настройка получателя — в [JSON настроек](../settings.md), пользовательские сценарии — в [инструкции интеграции](../students/03-service-desk.md).

## Три слоя

| Слой         | Пути                                          | Содержимое                                                                                      |
| ------------ | --------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| API          | `apps/service-desk/src/api`                   | Маршруты Fastify, JSON Schema, HTTP-коды, извлечение параметров и principal                     |
| Logic        | `apps/service-desk/src/logic`                 | Доступ к обращениям, проверка полей, выбор исполнителя, переходы, транзакционные сценарии и DTO |
| DAL          | `apps/service-desk/src/dal`                   | Drizzle-схема, запросы PostgreSQL, миграции и seed                                              |
| Общие модули | `libs/auth`, `libs/settings`, `libs/webhooks` | JWT и каталог Identity, JSON-хранилище, доставка событий с тем же делением по ответственности   |

Зависимости направлены `api → logic → dal`. API не обращается к БД напрямую; logic не импортирует Fastify; DAL не импортирует входящие HTTP-обработчики и прикладную логику. Исходящие HTTP, DNS и JWKS относятся к DAL.

`app.ts`, `runtime.ts`, `main.ts` и публичные `libs/**/index.ts` собирают зависимости. ESLint допускает там композицию, но эти исключения не предназначены для переноса бизнес-сценариев.

## Запуск и композиция

`main.ts` вызывает `buildRuntimeApp()` и открывает порт из активных настроек. `runtime.ts` создаёт JWT-адаптер, каталог сотрудников Keycloak, Swagger, модуль настроек и outbox worker. При `ui.enabled` и заданном `STATIC_DIR` он раздаёт собранный портал и SPA-маршруты.

`buildApp()` получает конфигурацию БД, проверку токена и `assigneeDirectory`. Объект `trainingDb` доступен точке композиции для поиска активной службы по доверенному `team_slug`. Параметры и зависимости передаются явно.

Неизвестный маршрут возвращает `404`, недопустимый запрос — `400`. Ожидаемые `DomainError`, `AuthError` и `SettingsError` преобразуются в контролируемые ответы. Неожиданные SQL/OIDC-подробности клиенту не выдаются. Неизвестные поля запроса отвергаются, а не удаляются валидатором молча.

## Данные Service Desk

Основная схема находится в `apps/service-desk/src/dal/schema.ts`.

| Таблица                 | Содержимое                                                               |
| ----------------------- | ------------------------------------------------------------------------ |
| `teams`                 | Slug службы, название и активность                                       |
| `training_users`        | Начальные и исторические записи; не источник текущих ролей Identity      |
| `api_tokens`            | Хеш совместимого статического токена, владелец, роль и срок              |
| `issues`                | Поля обращения, автор, статус, исполнитель, снимок его имени и `version` |
| `comments`              | Публичная переписка и внутренние заметки                                 |
| `issue_history`         | Автор, время и данные действия                                           |
| `webhook_subscriptions` | SQL-проекция получателей, их адреса и ключи подписи                      |
| `webhook_outbox`        | Снимки событий после изменений обращения                                 |
| `training_migrations`   | Имена, SHA-256 и время применения SQL-миграций                           |
| `webhook_deliveries`    | Состояния, попытки и lease доставок                                      |

Первые восемь таблиц описаны в Drizzle. Реестр миграций создаёт runner, таблицу доставок — `DeliveryStore.initialize()`. `CREATE TABLE IF NOT EXISTS` не обновляет существующую структуру; изменение таблицы доставок также требует явной миграции.

Запросы предметного DAL используют Drizzle. Специальный SQL блокировок, leases и `SKIP LOCKED` остаётся в DAL. Пользовательские значения не подставляются конкатенацией в SQL.

## Доступ и назначение

Сервер принимает только principal, полученный после проверки токена. Его `teamId` ограничивает чтение и изменение. Заявитель видит свои обращения, поддержка и администратор — обращения своего Service Desk. Недоступная карточка скрывается ответом `404`.

При создании сервер читает из Keycloak единственного активного пользователя с эффективной ролью `support-lead` и тем же `team_slug`. Если руководитель отсутствует, неоднозначен или каталог недоступен, возвращается `503` до начала записи обращения.

При переназначении каталог повторно проверяет активность, службу и эффективные роли кандидата. Предыдущий вход сотрудника в портал не требуется. В обращении сохраняются логин и снимок имени; этот снимок не доказывает текущую доступность сотрудника для нового назначения. Портал показывает исполнителя только для чтения, распределение реализует сервис студентов.

## Транзакции и конфликты

```text
Запрос → проверка API и logic → одна транзакция:
    обращение + история + outbox
→ commit → HTTP-ответ → отдельная доставка worker
```

Комментарии, назначения и переходы используют `issues.version`: обновление ограничено ID, службой и прежней версией. Если строка уже изменилась, операция возвращает `409`; её история, комментарий и событие откатываются вместе с обновлением. Это серверная проверка конкурентной записи, а не контракт клиентского `If-Match` для обращения.

Закрытие заявителем разрешено только для своего открытого обращения. Остальные рабочие переходы доступны поддержке и администратору. При закрытии статус, `assignee=null` и `assigneeDisplayName=null` сохраняются вместе; история содержит прежнего исполнителя, событие — уже очищенного.

Внутренние комментарии скрыты от заявителя. Их текст не включается в webhook. Отправка уведомления выполняется после commit и не откатывает обращение при сетевой ошибке.

## JSON настроек

`libs/settings` хранит документ `SETTINGS_FILE`; `config/backend.json` служит шаблоном только для отсутствующего файла. `GET/PUT/PATCH /api/settings` доступны администратору службы поддержки. PATCH объединяет вложенные поля с актуальным документом внутри очереди записи, PUT заменяет документ целиком. В обоих случаях сохраняется и проверяется полный документ.

Файл заменяется атомарно с fsync и правами `0600`. Очередь сериализует записи одного процесса; межпроцессной блокировки нет. `ETag` и `If-Match` защищают от устаревшей редакции. Секреты остаются в ENV; JSON допускает только фиксированные имена переменных.

Worker переносит адреса уведомлений из JSON в SQL без двойной записи со стороны settings API. Изменённый адрес применяется без перезапуска; остальные параметры — после перезапуска. Подробный контракт хранится в [настройках](../settings.md).

## Миграции и начальные данные

Новые SQL-файлы и метаданные находятся в `src/dal/migrations`. Изменение схемы проходит через `pnpm db:generate`, просмотр SQL/metadata и `pnpm db:migrate`. Применённые файлы не редактируются и не удаляются.

Runner читает `NNNN_name.sql` по порядку, проверяет уникальность номеров, SHA-256 и наличие применённых файлов. Новую миграцию нельзя вставить перед уже применённой. Весь upgrade проходит в одной транзакции под advisory lock; `CREATE INDEX CONCURRENTLY` с этим runner несовместим.

`seed.ts` создаёт `demo` только при отсутствии службы и не заменяет существующие токены. Изменения существующих данных выполняются отдельной миграцией или административной операцией. Пароли пользователей и роли Keycloak не копируются в предметный DAL.

Проверки выбираются по [матрице](../agents/verification.md). Корпоративные данные, пароли и автоматизации в этот контур не переносятся.
