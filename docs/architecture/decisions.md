# Архитектурные решения

Документ фиксирует причины текущего устройства стенда. Реализованные ограничения и контракты описаны в коде и связанных документах; изменение решения включает их обновление.

| Решение                                                   | Причина и следствие                                                                                                           |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Identity и Service Desk — отдельные приложения            | Сервис студентов подключается к ним как к внешним системам                                                                    |
| Приложение студентов находится в другом репозитории       | Для интеграции достаточно HTTP/OIDC-контрактов и выданного доступа к стенду                                                   |
| Keycloak с writable LDAP federation                       | Пользователи и пароли управляются в одной консоли и сохраняются в LDAP                                                        |
| Один PostgreSQL, одна БД, разные схемы                    | Service Desk использует `public`, Keycloak — `identity` с отдельной SQL-ролью; второй сервер БД не нужен                      |
| Доступ задают client roles Keycloak                       | Роли `customer`, `support`, `admin` и составная `support-lead` не зависят от LDAP-групп                                       |
| Браузерные приложения используют Code + PKCE S256         | Публичные клиенты не хранят секреты; password/direct grant и implicit flow выключены                                          |
| Service Desk проверяет JWT как resource server            | API не принимает пароль, не обменивает authorization code и не создаёт cookie-сессию                                          |
| Каталог сотрудников читается отдельным серверным клиентом | Текущие роли и активность доступны до первого входа сотрудника в портал; runtime не использует пароль администратора Keycloak |
| Новый запрос назначается одному руководителю поддержки    | Первоначальный адресат определён явно; последующее распределение реализует сервис студентов                                   |
| Портал показывает исполнителя без выбора                  | Интерфейс распределения остаётся частью студенческой задачи                                                                   |
| Обращение, история и outbox записываются вместе           | Сетевая доставка не блокирует транзакцию и не отменяет уже созданное обращение                                                |
| Webhook допускает повторы и не обещает порядок            | Получатель исключает дубликаты по ID события и при необходимости сверяет карточку через API                                   |
| JSON — источник настроек                                  | API сохраняет один документ; worker отдельно проецирует получателей в SQL                                                     |
| Jira Data Center 10.3 и явное подмножество                | Контракт не подменяется Cloud API, приватными browser endpoints или обещанием полной совместимости                            |
| Fastify, Nx, pnpm, Drizzle и три слоя                     | Один механизм сборки и зависимостей, направление `api → logic → dal`                                                          |
| Общая библиотека PrimeNG/Aura и SCSS                      | Готовые контролы и токены переиспользуются, feature-компоненты содержат раскладку                                             |
| RxJS применяется по задаче потока                         | Последовательные транзакционные `async/await` не переписываются без необходимости                                             |
| Пять Compose-сервисов                                     | PostgreSQL, LDAP, Identity, миграции и Service Desk с порталом/API; bootstrap — отдельный инструмент                          |

## Локальные правила Jira-совместимости

Снимок официальной спецификации — `10.3.27`, метаданные источника находятся в `docs/vendor/source.json`. Ранее исследованная корпоративная сборка — `10.3.16-QR-0016`; совпадение всех patch-возможностей не заявляется.

Форма `10001` моделирует замену оборудования и использует локальные type/option IDs. Формы `183` и `194` имеют собственные обязательные поля. Workflow также локальный: совпадение ID перехода и целевого статуса не является правилом Jira. Право заявителя закрыть своё обращение из любого открытого статуса — отдельная настройка стенда.

Публичный каталог содержит 14 операций. Очереди, JQL-поиск, отдельная история и дублирующая issue-карточка удалены. Новые методы добавляются только в согласованном объёме; [контракт](../api-compatibility.md) перечисляет поддерживаемое поведение.

## Совместимость и ограничения

Статические support/customer Bearer-токены сохранены как отключённый по умолчанию режим совместимости. `ADMIN_TOKEN` остаётся операторским доступом к настройкам. Они не заменяют Identity и не создают OIDC-сессию.

Нет автоматического создания службы Service Desk при добавлении пользователя Keycloak, массового сброса, внешних резервных копий и настройки публичного HTTPS. Docker-конфигурация сама не публикует сервер на VPS. Корпоративные пароли и данные не входят в seed и примеры.

Действующие SQL-миграции сохраняются неизменными. Смена решения, структуры данных или внешнего контракта оформляется новым изменением с подходящей [проверкой](../agents/verification.md).
