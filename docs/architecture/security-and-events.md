# Доступ и доставка событий

Service Desk проверяет access token Identity на каждом защищённом запросе. Браузерный вход выполняет Keycloak; API не принимает пароль, не обменивает authorization code и не создаёт cookie-сессию.

## Роль и служба определяются сервером

| Роль клиента `service-desk` | Доступ                                                                                 |
| --------------------------- | -------------------------------------------------------------------------------------- |
| `customer`                  | Свои обращения, публичная переписка и закрытие своего открытого обращения              |
| `support`                   | Обращения своей службы, рабочие переходы, внутренние заметки и назначение исполнителей |
| `support-lead`              | Наследует `support`; первоначальный исполнитель новых обращений                        |
| `admin`                     | Права поддержки и GET/PUT/PATCH `/api/settings`                                        |

Роли берутся из `resource_access.service-desk.roles`. LDAP-группы и роли клиента студентов не расширяют права Service Desk. Администратор realm Keycloak и администратор приложения — разные полномочия.

Доверенный `team_slug` связывается с существующей активной строкой `teams`. `teamId` из тела обращения не является правом доступа. Чтение и изменение ограничены своей службой; заявитель дополнительно ограничен авторством. Недоступная карточка возвращает `404`.

Пользователи и пароли создаются через Keycloak и сохраняются в LDAP. Атрибут `team_slug` отображается на LDAP `employeeType` и редактируется администратором. Добавление учётки не создаёт новую службу в БД.

## Проверка JWT

`libs/auth` использует `jose` и JWKS настроенного Identity. Проверяются RS256-подпись, точный issuer, audience `service-desk`, временные ограничения и обязательные `sub`, `iat`, `exp`. Payload `typ` должен равняться `Bearer`. ID token не принимается вместо access token.

Внутренний Docker-адрес может использоваться для запросов discovery/JWKS, но публичный issuer и `iss` не меняются. HTTP разрешён только для явно включённого локального режима; внешний контур требует HTTPS. Проверка TLS не отключается.

Невалидный токен даёт `401`; валидный токен без нужной роли или активной службы — `403`; недоступность проверки ключей — `503`. Ошибка Identity не подменяется демонстрационным principal.

Удаление роли или смена пароля не переписывают уже выданный JWT. Без отдельного механизма немедленного отзыва он может действовать до истечения срока. Активность службы проверяется API при обращении.

## Каталог исполнителей

`service-desk-directory` — отдельный confidential client с правами чтения пользователей и клиентов Identity. Его secret хранится только в ENV сервера. Runtime не использует пароль администратора Keycloak и не читает LDAP/таблицы Identity напрямую.

Кандидат должен быть включён, принадлежать нужному `team_slug` и иметь эффективную роль `support` или `admin`. Служебные учётки исключаются. Проверка выполняется заново при назначении, поэтому старый список не позволяет назначить отключённого сотрудника. Для начального назначения нужен ровно один включённый `support-lead` своей службы.

При закрытии заявителем или поддержкой статус, снятие исполнителя, история и outbox сохраняются одной транзакцией. Повторное закрытие заявителем возвращает `409`; остальные переходы для него запрещены.

## Секреты и совместимые токены

Пароли, ключи, тела токенов и Authorization не выводятся в журналы. HTTP-тело по умолчанию ограничено 128 КиБ; размер задаётся активной конфигурацией.

Совместимые статические токены хранятся как SHA-256 и проверяются по активности токена/службы и сроку. Режим по умолчанию отключён через `security.allowLegacyApiTokens=false`. Публичных методов выпуска и просмотра токенов нет. Операторский `ADMIN_TOKEN` сравнивается через `timingSafeEqual` с учётом длины и даёт доступ к настройкам, не к управлению Keycloak.

`WEBHOOK_SIGNING_SECRET` остаётся в ENV. Для каждой службы из её UUID выводится отдельный HMAC-ключ. JSON настроек не раскрывает ни мастер-секрет, ни ключ получателя; доступ к БД и резервным копиям требует защиты.

## Outbox и доставка

Обращение и событие сохраняются одной транзакцией. `DeliveryStore.prepare()` создаёт уникальную пару событие/подписка. Получатель должен быть включён до создания нужного уведомления; ответ `201` не подтверждает его доставку.

Доставка использует постоянную таблицу с `pending`, `sending`, `delivered`, `failed`. Claim выполняется через `FOR UPDATE SKIP LOCKED`, lease длится 30 секунд. После истечения lease незавершённая доставка может быть взята повторно. Worker не запускает перекрывающиеся циклы и при остановке ждёт текущую отправку.

По умолчанию за цикл выполняется до 20 отправок последовательно. Успех — любой `2xx`. Сетевая ошибка, `429` или `5xx` повторяются через 10 секунд, 1 минуту, 5 минут и 15 минут: всего до пяти попыток. Другие ответы и исчерпание повторов дают `failed`. Интервалы и ограничения задаются активными настройками.

Повторы возможны даже после успешного приёма: отправитель мог потерять ответ. Порядок событий не гарантируется. Получатель исключает дубликаты по `X-Training-Event-Id` и при необходимости сверяет карточку через API. DAL содержит просмотр и повтор доставок, но публичного HTTP-интерфейса для них нет.

## Адрес и подпись webhook

`libs/webhooks/dal/destination.ts` проверяет адрес при сохранении и перед отправкой:

- HTTPS, стандартный порт `443`, без userinfo и fragment;
- все найденные DNS-адреса публичны;
- частные, локальные и служебные IPv4/IPv6 запрещены;
- соединение использует проверенный адрес через `lookup`, сохраняя hostname для проверки TLS;
- перенаправления не выполняются.

Проверка адреса и последующий обычный `fetch(url)` недостаточны: повторное DNS-разрешение при соединении вернуло бы риск DNS rebinding. Текущая проверка использует собственный список диапазонов; обновление сетевых правил требует проверки. Отдельного deadline DNS lookup нет. HTTP использует socket timeout, по умолчанию 10 секунд, а не строгий общий deadline доставки.

`X-Training-Signature` содержит `sha256=<hex>` от HMAC-SHA256 исходных байтов JSON. Выданный ключ используется как UTF-8 строка. ID события и тело сохраняются при повторах. Пример получателя находится в [инструкции интеграции](../students/03-service-desk.md).

## Настройки и ограничения

`SETTINGS_FILE` — источник настроек. Запись атомарна с fsync, сериализуется внутри одного процесса и не поддерживает независимых writers одного файла. Worker отдельно переносит получателей в SQL; удалённая JSON-запись отключает управляемую подписку, сохраняя историю. Подробности — в [настройках](../settings.md).

Автоматического удаления истории/outbox, гарантированного порядка, отдельного dead-letter брокера и мгновенного отзыва всех JWT нет. Хранилище растёт без политики retention. Изменения доступа, подписей, адресов и повторов проверяются по [матрице](../agents/verification.md).
