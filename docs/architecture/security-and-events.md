# Identity, JWT-доступ и доставка событий

Контракты — в [api-compatibility.md](../api-compatibility.md), управление Identity — в [identity.md](../identity.md), контейнеры — в [docker.md](../docker.md). Приложение студентов отдельно; наш портал встроен в Service Desk и использует `keycloak-js`. Сервер API не принимает пароль, не обменивает code и не создаёт cookie-сессию. Клиентский `/auth/callback` обрабатывается SDK, не серверным RP.

## Кто и куда имеет доступ

| Учётные данные                                                       | Область доступа                                                                         |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| JWT с ролью клиента `service-desk:customer` или customer bearer      | Метаданные форм, собственные обращения, публичные сообщения и закрытие своего обращения |
| JWT с ролью клиента `service-desk:support` или support bearer        | Обращения своего Service Desk, рабочие переходы и внутренние заметки                    |
| JWT с ролью клиента `service-desk:admin` или bootstrap `ADMIN_TOKEN` | `GET/PUT/PATCH /api/settings`: весь JSON настроек                                       |

Роли определяются по `resource_access["service-desk"].roles`, а не LDAP-группе или роли студенческого клиента. Keycloak realm admin и роль администратора API не тождественны. Авторизация выполняется только над проверенным токеном.

Совместимые статические Bearer-токены проверяются по SHA-256, активности токена и раздела, сроку действия. HTTP-методов выпуска и просмотра таких токенов нет. Рабочая конфигурация по умолчанию отключает статические support/customer bearer через `security.allowLegacyApiTokens=false`; тестовый buildApp сохраняет отдельную compatibility-настройку. Bootstrap-секрет сравнивается с учётом длины через `timingSafeEqual`. Такой секрет не служит JWT Identity и не используется для управления Keycloak.

`teamId` не принимается из тела обращения как право доступа. Команда определяется из principal; JWT содержит административно заданный `team_slug`. API проверяет наличие/активность соответствующей команды. Новая учётная запись Keycloak не создаёт API-команду автоматически. Tenant-фильтр в DAL защищает каждое чтение и изменение.

## Identity и LDAP federation с записью

Identity работает на Keycloak с общей PostgreSQL и схемой `identity`. Пользователи и пароли создаются/изменяются через Keycloak Admin Console и сохраняются в общем LDAP через writable federation. `team_slug` отображается на LDAP `employeeType`; управление атрибутом принадлежит администратору. Keycloak управляет ролями клиента `customer`, `support`, `admin` и composite-ролью `support-lead`. LDAP-группы не являются политикой доступа Service Desk.

Приложение студентов — отдельный публичный OIDC-клиент `student-service` с Authorization Code + PKCE S256. Direct Access Grants/password flow отключён. Identity выдаёт access token с audience `service-desk` и роли клиента API. Service Desk не получает пароль и не обращается к LDAP для проверки каждого запроса.

Корпоративный сценарий показал OIDC через ADFS, но не доказал прямой LDAP. Учебная реализация Keycloak + LDAP самостоятельна и не подключает корпоративные аккаунты. Учётные данные LDAP доступны только оператору/Identity. Изолированные ветки и отдельные bind DN команд не реализованы; нельзя выдавать общий reader как ограниченный доступ одной команды.

## Проверка JWT на сервере

`libs/auth` использует `jose` для проверки подписи по JWKS, точного issuer, audience и временных claims. Разрешён RS256; обязательны `exp`, `iat`, `sub`, поле `typ` в теле токена должно быть `Bearer`. Приложение передаёт **access token** в `Authorization: Bearer`; ID token не заменяет access token API. Не доверять непроверенному телу JWT и не подменять issuer внутренним Docker-именем.

При запросах сервера к внутреннему адресу Identity публичный issuer и `iss` остаются неизменны. Локальный HTTP разрешается явно только в разработке; для внешнего контура нужен HTTPS. Проверка сертификата не отключается ради успешного подключения.

Недействительный/истёкший токен не создаёт principal. Валидная аутентификация без нужной роли или команды не даёт допуск. API не создаёт собственную браузерную сессию: прежние `/training/auth/login|session|logout` и OIDC start/callback больше не предоставляются. Secret OIDC-клиента для проверки JWT не нужен.

Отзыв роли или смена пароля в Identity не переписывает уже выданный JWT. До истечения срока токен может сохранять прежние claims; немедленная introspection/revocation каждого запроса отдельно не заявляется. Отключение SQL-команды проверяется при обращении к API.

Размер HTTP-тела ограничен 128 КиБ. Authorization и другие секретные заголовки редактируются в логах; тела токенов, пароли, bootstrap/API-токены и webhook-секреты не логируются. Мастер-секрет `WEBHOOK_SIGNING_SECRET` остаётся в ENV. Для адреса уведомлений команды из JSON выводится отдельный HMAC-ключ от UUID команды; sender SQL-проекция хранит его для подписи. JSON/API settings не раскрывают ключ. Доступ к БД и backup требует защиты.

## Outbox и доставки

`RequestLogic` сохраняет `webhook_outbox` в той же транзакции, что изменение обращения и историю. Тело события содержит снимок обращения и тип `jira:issue_created` либо `jira:issue_updated`. Текст внутренних комментариев туда не включается.

Обработчик `libs/webhooks/logic/worker.ts` по умолчанию раз в секунду:

1. Создаёт `webhook_deliveries` для активных подписок той же команды, зарегистрированных не позже события.
2. Уникальность `(event_id, subscription_id)` предотвращает дубли строк доставки.
3. DAL забирает готовую доставку через `FOR UPDATE SKIP LOCKED`, ставит `sending`, увеличивает attempt и выдаёт lease на 30 секунд.
4. HTTPS-адаптер отправляет событие; DAL сохраняет результат.

Истёкшая lease позволяет подобрать `sending` после сбоя процесса. Один worker не запускает перекрывающиеся циклы; за цикл выполняется до 20 доставок последовательно. При остановке он ожидает текущую доставку и закрывает соединение. Это не exactly-once: получатель мог принять запрос до сбоя отправителя, поэтому дубликаты допустимы. Порядок доставки событий по обращении не гарантируется.

Ответ `2xx` переводит доставку в `delivered`. Сетевая ошибка, `429` и `5xx` повторяются через 10 секунд, 1 минуту, 5 минут, 15 минут — до пяти попыток суммарно. Остальные ответы, включая перенаправления, завершаются `failed`; исчерпание повторов также даёт `failed`. Это конечное состояние ошибки в таблице, а не отдельная очередь dead-letter.

DAL поддерживает просмотр последних 100 доставок и повтор доставки вне состояния `sending`; публичных HTTP-методов для этих операций нет. Повтор сбрасывает число попыток, сохраняя ID и исходное тело события. Это политика стенда, она не определяет поведение Jira.

## HTTPS и защита адреса webhook

Адрес проверяется при регистрации и перед каждой отправкой в `libs/webhooks/dal/destination.ts`:

- только HTTPS, порт 443, без userinfo и fragment;
- все разрешённые DNS-адреса должны пройти проверку публичности;
- частные/локальные/служебные IPv4 и недопустимые IPv6 отклоняются;
- транспорт подключается к проверенному адресу через собственный `lookup`, сохраняя исходный HTTPS hostname для проверки TLS;
- перенаправления не выполняются; тело ответа не загружается целиком.

Не заменять этот транспорт обычным `fetch(url)` после отдельной DNS-проверки: повторное разрешение имени при соединении вернёт риск DNS rebinding. Публичность проверяется собственной функцией диапазонов, а не внешним справочником; новые сетевые диапазоны и правила нужно проверять отдельно. DNS lookup не имеет отдельного deadline; HTTP использует 10-секундный socket timeout, это не строгий общий deadline всей доставки.

Подпись — HMAC-SHA256 сырых байтов JSON с секретом подписки. Заголовки `X-Training-Signature: sha256=<hex>` и `X-Training-Event-Id` — собственный протокол стенда. Event ID стабилен при повторах; получатель использует его для дедупликации. Формат тела и подпись менять только вместе с документацией и тестами.

## Ограничения для будущих изменений

Не заявлять наличие автоматического согласования API-команд с LDAP/Keycloak, retention/очистки истории и outbox, гарантированного порядка событий, отдельного dead-letter брокера или немедленного отзыва всех выданных JWT при изменении роли: этого сейчас нет. Хранилище растёт без автоматической политики удаления.

Проверки доступа, публичности комментариев, issuer/audience/JWKS, обходов адреса webhook, повторов и восстановлений lease обязательны при изменении соответствующих модулей. Безопасный отказ важнее молчаливого fallback на demo-токен, незащищённый LDAP или внутренний адрес.

## Постоянные настройки

Правила JSON, API ролей и применение настроек описаны в [settings](../settings.md). Настройки доступны только администратору службы поддержки через GET/PUT/PATCH /api/settings; JSON содержит только разрешённые имена переменных окружения, не секретные значения. Настройки записываются в постоянный файл атомарно с fsync, но блокировка внутри процесса не позволяет запускать несколько независимых процессов записи одного файла. Worker проецирует адреса уведомлений в SQL отдельно; успешный PUT не доказывает HTTP-доставку.

Заявитель получает в GET transitions только закрытие собственного незакрытого обращения. POST повторно проверяет владельца, Service Desk, текущий статус и обязательные поля; иные переходы для заявителя запрещены. Изменение состояния/история/outbox атомарны и используют version check.
