## Минимальный публичный API

Сохранены 10 методов Jira-совместимого подмножества:

| Метод | Путь после `/rest`                                     | Назначение                                       |
| ----- | ------------------------------------------------------ | ------------------------------------------------ |
| GET   | `/servicedeskapi/servicedesk/3/requesttype/{id}/field` | Поля формы                                       |
| GET   | `/servicedeskapi/request`                              | Список обращений с пагинацией и фильтром статуса |
| POST  | `/servicedeskapi/request`                              | Создание обращения, 201                          |
| GET   | `/servicedeskapi/request/{key}`                        | Карточка обращения                               |
| GET   | `/servicedeskapi/request/{key}/comment`                | Переписка, пагинация start/limit                 |
| POST  | `/servicedeskapi/request/{key}/comment`                | Сообщение, 201                                   |
| GET   | `/api/2/issue/{key}/transitions`                       | Доступные изменения статуса                      |
| POST  | `/api/2/issue/{key}/transitions`                       | Изменение статуса, 204                           |
| GET   | `/api/2/user/assignable/search`                        | Доступные исполнители из Identity                |
| PUT   | `/api/2/issue/{key}/assignee`                          | Назначить или снять исполнителя, 204             |

Все `/rest` требуют входа. Заявитель читает свои обращения и публичные сообщения, сотрудник поддержки и администратор — обращения своего Service Desk. Рабочие изменения статуса и внутренние заметки доступны поддержке и администратору. Заявитель может закрыть своё обращение.

Собственные методы: `GET /api/me` и `GET/PUT/PATCH /api/settings` (последние только администратору). Итого 14 операций в Swagger. `/api/config` и `/health` обслуживают запуск портала и инфраструктуру и не входят в каталог Swagger.

Удалены отдельные очереди, поиск/JQL, список типов, история и дублирующая карточка issue. Они возвращают 404. Новые обращения поступают интеграции через webhook; по ключу читается карточка. В DTO не выдаются необязательные ссылки на удалённые методы.

## Пример создания

```json
{
    "serviceDeskId": "3",
    "requestTypeId": "10001",
    "requestFieldValues": {
        "customfield_12900": "AB-1234",
        "description": "Нужна замена неисправного ноутбука",
        "customfield_20001": { "id": "20002" },
        "customfield_20002": { "id": "20101" }
    }
}
```

Обязательность и значения 183/194 основаны на исследованных корпоративных формах, но без вложений и участников. Тема формируется из имени типа запроса. Автоматизации корпоративного бота, сроки и метка первой линии не эмулируются.

## Учебный тип 10001: замена оборудования

Service desk — `3`, request type — `10001`. Это новая учебная конфигурация, а не полученный из корпоративной Jira тип. ID полей выбора и options ниже не следует переносить в production. Исследованные формы `183`/`194` сохраняют свою прежнюю семантику.

Метаданные: `GET /rest/servicedeskapi/servicedesk/3/requesttype/10001/field`. Все четыре поля обязательны; строки непустые, select передаётся объектом `{ "id": "..." }`.

| Поле                | Название            | Формат и допустимые значения                                                                             |
| ------------------- | ------------------- | -------------------------------------------------------------------------------------------------------- |
| `customfield_12900` | Имя устройства      | Строка, например `TRAINING-PC-01`                                                                        |
| `description`       | Описание            | Строка с описанием запроса                                                                               |
| `customfield_20001` | Что нужно заменить? | Option: `20001` — ПК, `20002` — Ноутбук, `20003` — Монитор, `20004` — Периферия для ПК, `20005` — Другое |
| `customfield_20002` | Причина замены      | Option: `20101` — Поломка, `20102` — Устаревшее оборудование, `20103` — Другая причина                   |

```json
{
    "serviceDeskId": "3",
    "requestTypeId": "10001",
    "requestFieldValues": {
        "customfield_12900": "TRAINING-PC-01",
        "description": "Учебная заявка: требуется замена устройства",
        "customfield_20001": { "id": "20002" },
        "customfield_20002": { "id": "20101" }
    }
}
```

Этот JSON отправляется в `POST /rest/servicedeskapi/request` с JWT роли customer либо статическим customer bearer; успех — `201` с созданной обращением. Создание пишет `jira:issue_created` в outbox. Доставка произойдёт только при зарегистрированной подписке команды и доступном разрешённом HTTPS-получателе; одного ответа `201` недостаточно для утверждения о доставке webhook.

## Workflow

Учебные ID переходов совпадают с ID целевых статусов **по нашей конфигурации**. Это упрощение стенда, не правило Jira. Клиент должен всегда читать transitions и передавать возвращённый ID.

| Статус             | ID    | Доступные целевые ID |
| ------------------ | ----- | -------------------- |
| Новая              | 10005 | 10006                |
| Ожидает выполнения | 10006 | 10007, 10008, 10009  |
| Уточнение          | 10007 | 10006                |
| В работе           | 10008 | 10006, 10007, 10010  |
| Отложена           | 10009 | 10006                |
| Проверка           | 10010 | 10008, 10011         |
| Закрыта            | 10011 | Нет                  |

Переход в «Закрыта» требует `fields.resolution.id="10100"`. Полная корпоративная схема, transition IDs и экраны не получены; указанная таблица — явная учебная модель. Одновременная запись конфликтующих изменений возвращает 409. История сохраняется сервером в транзакции; отдельного REST для неё нет.

## Webhook

`jira:issue_created` и `jira:issue_updated` содержат снимок обращения. Тела внутренних комментариев в тело события не включаются. Каждая пара событие/подписка уникальна в БД. Доставка имеет семантику **at least once**: возможны дубликаты при сбое после приёма получателем.

Заголовки собственного учебного протокола:

- `X-Training-Event-Id`: постоянный ID события.
- `X-Training-Signature`: `sha256=` + hex HMAC-SHA256 **сырых байтов тела** с секретом подписки.

Успех: 2xx. Сетевая ошибка, 429 и 5xx повторяются через 10 секунд, 1 минуту, 5 минут, 15 минут. Другие ответы, включая перенаправления, завершают доставку ошибкой. Это политика стенда, не обещание поведения Jira. URL должен использовать HTTPS порт 443 без имени пользователя и пароля в URL. Проверяется публичность всех DNS-адресов; соединение закрепляется за проверенным адресом, перенаправления не выполняются.

Новые подписки не получают события, созданные до регистрации. Повторная отправка существующей доставки сохраняет ID события.

## Identity и авторизация API

Identity — отдельный Keycloak со схемой `identity` в общей БД и LDAP federation с записью. Пользователи/пароли управляются через Keycloak Admin Console, роли — через роли клиента `service-desk`. LDAP-группы больше не используются для определения доступа в API. Студенческое приложение находится в отдельном репозитории и подключается к публичный клиент `student-service` через Authorization Code + PKCE S256. Параметры — в [identity.md](identity.md).

Service Desk проверяет JWT: принимает access token в `Authorization: Bearer`, проверяет RS256-подпись по JWKS, issuer, audience `service-desk`, срок действия и тип access token. Principal использует проверенные `preferred_username`, `team_slug` и `resource_access["service-desk"].roles`. Команда должна существовать и быть активной в SQL. Роли другого клиента или непроверенное тело JWT не дают доступа.

- `customer` — собственные обращения и публичные комментарии.
- `support` — очереди/поиск/workflow и обращения своей команды.
- `admin` — административные операции Service Desk.

Сервер не принимает пароль, не обменивает authorization code и не хранит секрет публичного OIDC-клиента. Серверных `/training/auth` login/logout/session/start/callback endpoints нет; `/auth/callback` обслуживает только встроенный UI/SDK. Встроенный портал использует публичный клиент `service-desk-test`, `keycloak-js` и Bearer access token; пароль вводится в отдельном Identity. ID token не используется вместо API access token.

Статические support/customer bearer поддерживаются для совместимости, но default runtime `security.allowLegacyApiTokens=false`; bootstrap `ADMIN_TOKEN` сохраняется. Они не создают SSO-сессию и не управляют пользователями Keycloak. Отключение API-команды применяется при запросе; смена роли/пароля Identity не означает немедленное переписывание уже выданного JWT.

## Собственные settings endpoints

Собственный API настроек: `GET/PUT/PATCH /api/settings`, полный JSON без обёртки; доступ только администратору службы поддержки, ответ 200. Ревизии и применение изменений — в [settings](settings.md). `/api/me` возвращает текущую учётную запись, `/api/config` — публичные параметры входа. Отдельных административных API команд, токенов и подписок больше нет.

Список поддерживает `start`, `limit` (1–100) и `requestStatus=ALL_REQUESTS|OPEN_REQUESTS|CLOSED_REQUESTS`. Заявитель получает только свои обращения, поддержка и администратор — обращения своего Service Desk. Просмотр всех обращений поддержки — явное локальное расширение стандартного customer-list сценария Jira. Порядок — по последней активности; ссылки пагинации сохраняют фильтр.

## Закрытие обращения заявителем

Через существующие GET/POST `/rest/api/2/issue/{key}/transitions` заявитель получает только закрытие своего незакрытого обращения. В локальном workflow это переход `10011` с `resolution.id=10100`; значения берутся из GET с `expand=transitions.fields`, а не задаются клиентом вслепую. POST отвечает 204, карточка получает статус «Закрыта», обращение появляется в CLOSED_REQUESTS. История и `jira:issue_updated` сохраняются вместе с изменением статуса в одной транзакции.

Это явное локальное расширение права заявителя: закрытие из любого незакрытого статуса. Другие изменения статуса заявителю запрещены (403), чужое обращение недоступно (404), повторное закрытие возвращает 409. Рабочие переходы поддержки не изменены. Новых REST-методов нет.

Формат перехода и метаданные полей сверены с pinned 10.3 OpenAPI и [официальным Data Center Issue API](https://developer.atlassian.com/server/jira/platform/rest/v10000/api-group-issue/); конкретные IDs и права локального workflow не являются универсальными значениями Jira.

## Исполнитель

- `GET /rest/api/2/user/assignable/search`: доступные сотрудники из Keycloak; поддерживаются `username`, `issueKey`, `project=HELP`, `maxResults` (по умолчанию 50, максимум 100). Неподдерживаемые параметры отвергаются. `startAt` не добавлен, поскольку отсутствует в pinned 10.3 контракте.
- `PUT /rest/api/2/issue/{key}/assignee`: `{ "name": "username" }` назначает, `{ "name": null }` снимает исполнителя; ответ 204. Автоназначение через `name=-1` не поддерживается.

Эти методы предназначены для поддержки/администратора и интеграции студентов. В нашем портале исполнитель отображается без выбора. Список кандидатов содержит только включённых сотрудников поддержки своего Service Desk с эффективной ролью `support`/`admin` (включая composite `support-lead`); при назначении данные проверяются заново в Identity, без требования предыдущего входа кандидата в Service Desk. Чужой раздел недоступен; отключённый/лишённый роли кандидат не назначается.

Новое обращение сразу назначается единственному включённому руководителю своего Service Desk (`support-lead`). Если руководителя нет или их несколько, создание возвращает 503 без частично созданного обращения. Дальнейшее распределение определяет студенческий сервис. При закрытии исполнитель и его отображаемое имя очищаются вместе со статусом/историей/outbox.

Карточка и список запросов имеют документированное локальное расширение CustomerRequestDTO: `assignee: {name,key,displayName}|null`. Это сохранённый снимок, не заявление об актуальной доступности сотрудника. Webhook использует стандартное поле `issue.fields.assignee`; назначение, снятие и закрытие формируют `jira:issue_updated`.
