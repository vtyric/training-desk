# Контракт API и отличия от Jira

Стенд реализует 10 методов выбранного подмножества Jira Service Management Data Center 10.3 и четыре собственные операции. Это не полная установка Jira. Источники и точная версия сохранённой спецификации находятся в [source.json](vendor/source.json); snapshot — [jira-10.3.openapi.json](vendor/jira-10.3.openapi.json).

Исследованная корпоративная версия — `10.3.16-QR-0016`, сохранённая справка ветки 10.3 — `10.3.27`. Совпадение всех особенностей этих сборок не заявляется. Cloud API и приватные браузерные endpoints не используются.

## Поддерживаемые методы

| Метод | Путь                                                        | Успех                             |
| ----- | ----------------------------------------------------------- | --------------------------------- |
| GET   | `/rest/servicedeskapi/servicedesk/3/requesttype/{id}/field` | `200`, поля формы                 |
| GET   | `/rest/servicedeskapi/request`                              | `200`, список                     |
| POST  | `/rest/servicedeskapi/request`                              | `201`, созданное обращение        |
| GET   | `/rest/servicedeskapi/request/{key}`                        | `200`, карточка                   |
| GET   | `/rest/servicedeskapi/request/{key}/comment`                | `200`, сообщения                  |
| POST  | `/rest/servicedeskapi/request/{key}/comment`                | `201`, сообщение                  |
| GET   | `/rest/api/2/issue/{key}/transitions`                       | `200`, разрешённые переходы       |
| POST  | `/rest/api/2/issue/{key}/transitions`                       | `204`                             |
| GET   | `/rest/api/2/user/assignable/search`                        | `200`, сотрудники                 |
| PUT   | `/rest/api/2/issue/{key}/assignee`                          | `204`                             |
| GET   | `/api/me`                                                   | `200`, проверенная учётная запись |
| GET   | `/api/settings`                                             | `200`, весь JSON                  |
| PUT   | `/api/settings`                                             | `200`, полная замена JSON         |
| PATCH | `/api/settings`                                             | `200`, частичная правка JSON      |

Swagger доступен на `/docs/`, OpenAPI — `/docs/json`. Authorize использует Identity, Logout очищает авторизацию и завершает SSO-сеанс. Схемы и группы описывают все 14 операций. Публичные `/health` и `/api/config` обслуживают инфраструктуру и портал и скрыты из каталога Swagger.

Отдельные очереди, JQL-поиск, список типов, история и дублирующая карточка issue не реализованы и возвращают `404`.

## Права и область данных

API принимает access token с issuer стенда, audience `service-desk`, ролью клиента `service-desk` и `team_slug` активной службы. Заявитель читает только свои обращения и публичные сообщения. Поддержка и администратор работают с обращениями своей службы; настройки доступны только администратору.

Технические роли: `customer`, `support`, `admin`; `support-lead` наследует `support`. Эффективную роль возвращает `/api/me`. Непроверенные поля тела не меняют права или принадлежность к службе.

Совместимые статические токены существуют для старых сценариев, но рабочая настройка `security.allowLegacyApiTokens=false` отключает их. `ADMIN_TOKEN` остаётся отдельным операторским доступом к настройкам. Клиент студентов использует обычный access token.

## Форма замены оборудования

Service Desk имеет ID `3`, тип замены — `10001`. Это локальная учебная конфигурация: ID типа и вариантов не заявляются как значения корпоративной Jira. Формы `183` и `194` поддерживаются отдельно; обязательность и варианты берутся из метаданных соответствующей формы.

Все четыре поля типа `10001` обязательны:

| Поле                | Значение                                                                                                 |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| `customfield_12900` | Непустая строка с названием устройства                                                                   |
| `description`       | Непустая строка описания                                                                                 |
| `customfield_20001` | `{id}`: `20001` — ПК, `20002` — ноутбук, `20003` — монитор, `20004` — периферия для ПК, `20005` — другое |
| `customfield_20002` | `{id}`: `20101` — поломка, `20102` — устаревшее оборудование, `20103` — другая причина                   |

Пример тела POST:

```json
{
    "serviceDeskId": "3",
    "requestTypeId": "10001",
    "requestFieldValues": {
        "customfield_12900": "AB-1234",
        "description": "Ноутбук не включается",
        "customfield_20001": { "id": "20002" },
        "customfield_20002": { "id": "20101" }
    }
}
```

Заголовок обращения формируется из типа. `raiseOnBehalfOf` и непустые `requestParticipants` не поддерживаются. Вложения, SLA и корпоративные автоматизации не воспроизводятся.

Новое обращение назначается единственному активному руководителю своей службы из Identity. При ошибке определения руководителя возвращается `503` без записи обращения/history/outbox. Успех `201` подтверждает сохранение, но не доставку уведомления.

## Списки и переписка

Список обращений принимает `start` от 0, `limit` от 1 до 100 (по умолчанию 25), `requestStatus=ALL_REQUESTS|OPEN_REQUESTS|CLOSED_REQUESTS`. Порядок — по последней активности и ID, от новых к старым. Ответ содержит `values`, `size`, `start`, `limit`, `isLastPage` и ссылки, сохраняющие фильтр.

Для поддержки список всех обращений своей службы — локальное расширение customer-list Jira. Открытость определяется отсутствием resolution, закрытость — его наличием.

Комментарии используют `start/limit`. POST требует `body` и `public`; `public=false` доступен поддержке/администратору. Внутренние сообщения не возвращаются заявителю, их текст не включается в webhook.

## Исполнитель

Поиск принимает `username`, `issueKey`, `project=HELP`, `maxResults` от 1 до 100 (по умолчанию 50). `username` фильтрует логин и имя. `startAt` и прочие неподдерживаемые параметры отвергаются.

Кандидаты — включённые пользователи своего Service Desk с эффективной ролью `support` или `admin`, включая руководителя. При назначении каталог проверяется заново. Предыдущий вход кандидата в портал не нужен.

PUT принимает `{ "name": "support" }` либо `{ "name": null }`. Значение `-1` не поддерживается. Повтор того же назначения не создаёт лишнюю запись, но доступность кандидата проверяется. Снятие назначения возможно и при недоступном каталоге.

Карточка и список содержат локальное расширение CustomerRequestDTO: `assignee: {name,key,displayName}|null`. Это сохранённый снимок, а не признак текущей доступности сотрудника. Webhook использует `issue.fields.assignee`.

## Статусы и закрытие

Клиент получает переходы через GET; `expand=transitions.fields` добавляет обязательные поля. ID перехода передаётся из ответа. В локальной модели он совпадает с ID целевого статуса, но это не общее правило Jira.

| Статус             | ID      | Следующие статусы поддержки |
| ------------------ | ------- | --------------------------- |
| Новая              | `10005` | `10006`                     |
| Ожидает выполнения | `10006` | `10007`, `10008`, `10009`   |
| Уточнение          | `10007` | `10006`                     |
| В работе           | `10008` | `10006`, `10007`, `10010`   |
| Отложена           | `10009` | `10006`                     |
| Проверка           | `10010` | `10008`, `10011`            |
| Закрыта            | `10011` | Нет                         |

Закрытие требует `fields.resolution.id="10100"`. Заявителю доступно только закрытие своего обращения из любого открытого статуса; это локальное расширение прав. Другие переходы дают `403`, чужая карточка — `404`, повторное закрытие заявителем — `409`.

Закрытие атомарно меняет статус, снимает исполнителя и его отображаемое имя, сохраняет историю и `jira:issue_updated` с `assignee=null`. Конфликт версии откатывает действие с `409`.

## Уведомления

События `jira:issue_created` и `jira:issue_updated` содержат снимок обращения. Пара событие/подписка уникальна в БД, но при сбое после приёма получателем доставка может повториться; общий порядок не гарантируется.

- `X-Training-Event-Id` — стабильный ID события.
- `X-Training-Signature` — `sha256=` и HMAC-SHA256 исходного тела.
- Ключ получателя используется как UTF-8 строка; мастер-секрет остаётся на сервере.

Любой `2xx` означает успех. Сеть, `429` и `5xx` повторяются с настроенными задержками; прочие ответы становятся ошибкой доставки. По умолчанию задержки — 10 секунд, 1, 5 и 15 минут. Доставки хранятся в БД с арендой обработки; перезапуск не сбрасывает их. Это собственный протокол стенда, не обещание полной совместимости webhook Jira.

Получатель — публичный HTTPS URL на порту `443`. DNS проверяется перед соединением и закрепляется для запроса, перенаправления не выполняются. Локальная интеграция использует HTTPS-туннель. Примеры получателя и проверки подписи — в [третьей инструкции](students/03-service-desk.md).

JSON настроек, PATCH, редакции и применение параметров описаны в [settings](settings.md). Создание пользователей/ролей — в [первой инструкции](students/01-keycloak-and-roles.md), OIDC — во [второй](students/02-openid-connect.md).
