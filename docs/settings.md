# Настройки Service Desk

Источник настроек — один JSON-документ. `config/backend.json` служит шаблоном; рабочий файл создаётся из него только при отсутствии `SETTINGS_FILE`. В Docker это `/data/settings/backend.json` на постоянном томе, локально — `.local/settings/backend.json`.

## API настроек

Все три метода доступны только роли `service-desk:admin` либо операторскому `ADMIN_TOKEN`. Для обычного входа используется JWT администратора приложения.

| Метод                 | Тело запроса          | Результат                 |
| --------------------- | --------------------- | ------------------------- |
| `GET /api/settings`   | Нет                   | Полный JSON               |
| `PUT /api/settings`   | Полный JSON из GET    | Полная замена             |
| `PATCH /api/settings` | Изменяемая часть JSON | Изменение указанных полей |

Успех — `200` с полным сохранённым документом, `ETag`, `Cache-Control: no-store` и `X-Restart-Required`. Обёртки `config` нет. Без входа возвращается `401`, без прав — `403`.

## Состав документа

| Поле       | Содержимое                                                              |
| ---------- | ----------------------------------------------------------------------- |
| `version`  | Версия структуры, сейчас `1`                                            |
| `revision` | Номер редакции, увеличивается сервером при сохранении                   |
| `server`   | Адрес, порт, ограничение тела запроса                                   |
| `database` | Имя ENV подключения и размер пула                                       |
| `identity` | Issuer, audience, клиент каталога и имя ENV его секрета, таймаут        |
| `service`  | Название, ключ проекта `HELP`, идентификатор портала `3`                |
| `webhooks` | Интервал обработки, таймаут, размер порции и задержки повторов          |
| `ui`       | Параметры портала и браузерного входа                                   |
| `security` | Режим совместимости со статическими API-токенами; по умолчанию отключён |
| `teams`    | Получатели уведомлений, по одному на UUID службы                        |

Секретные значения не хранятся в JSON и не возвращаются API. Допустимые имена переменных окружения фиксированы валидатором; ссылка на произвольную ENV не принимается.

## Частичное изменение

Пример PATCH одного поля:

```json
{
    "server": {
        "port": 3001
    }
}
```

Остальные поля сохраняются. Объекты объединяются рекурсивно, массивы заменяются целиком. Корневой объект должен содержать хотя бы одно поле. Неизвестные поля, опасные имена ключей и `null` возвращают `400`. `version` и `revision` в PATCH не передаются.

После объединения сервер проверяет весь документ и адреса получателей. Проверка и запись выполняются внутри одной очереди: параллельные изменения разных полей не затирают друг друга. Некорректный документ не записывается.

## Получатель уведомлений

`teamId` из `GET /api/me` — ключ записи в `teams`. Это UUID, а не slug `demo`. Для новой записи нужны все поля:

```json
{
    "teams": {
        "00000000-0000-4000-8000-000000000001": {
            "webhook": {
                "id": "00000000-0000-4000-8000-000000000001",
                "url": "https://receiver.example/webhooks/service-desk",
                "enabled": true,
                "createdAt": "2026-11-08T09:00:00.000Z"
            }
        }
    }
}
```

Вместо UUID и URL используются реальные значения. Этот фрагмент подходит для PATCH. Когда запись существует, PATCH может менять только `webhook.url` или `enabled`. Сервер сохраняет исходное время создания; `id` совпадает с ключом.

URL должен быть публичным HTTPS-адресом на порту `443`, без credentials и fragment. Внутренние адреса и перенаправления запрещены. Уже настроенного получателя можно отключить при недоступном DNS, не меняя URL.

Удаление записи возможно через PUT полного документа без неё. Обработчик отключит соответствующую SQL-подписку; история доставок сохранится. Пустой объект в PATCH запись не удаляет.

Для одной общей службы URL общий: команды с `team_slug=demo` заменяют получателя друг друга. Изолированные команды требуют отдельных подготовленных служб или экземпляров стенда.

## Конфликты и применение

PUT передаёт `revision` последнего GET. Необязательный `If-Match` должен совпадать с ним. PATCH использует необязательный `If-Match` без номера редакции в теле. Пример заголовка: `If-Match: "7"`.

Устаревшая редакция даёт `409`, несовпадение заголовка и тела PUT — `400`. После конфликта нужна актуальная версия GET и повторное внесение правки.

Адреса уведомлений применяются на следующем цикле обработчика без перезапуска. Уже начатая доставка может использовать прежний URL. Остальные параметры активируются после перезапуска Service Desk; `X-Restart-Required: true` сообщает о необходимости. Успешное сохранение не подтверждает доставку webhook.

Файл записывается атомарной заменой с fsync и правами `0600`. Очередь защищает записи внутри одного процесса; распределённой блокировки для нескольких независимых писателей нет.

Подключение локального получателя, curl-примеры и HMAC — в [инструкции интеграции](students/03-service-desk.md).
