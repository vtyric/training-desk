# Identity и доступ к Service Desk

Identity работает на Keycloak и хранит настройки в схеме `identity` общей БД PostgreSQL. Пользователи и пароли находятся в LDAP; ими можно управлять через Keycloak Admin Console. Service Desk проверяет выданные Identity токены и права пользователя. Пароль вводится только на странице Identity.

Этот документ описывает подключение отдельного сервиса студентов. Его интерфейс и обработка обращений разрабатываются в другом репозитории.

## Параметры подключения

| Параметр                           | Локальное значение                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------- |
| Issuer                             | `http://localhost:8081/realms/training`                                                   |
| Discovery                          | `http://localhost:8081/realms/training/.well-known/openid-configuration`                  |
| Realm                              | `training`                                                                                |
| Управление пользователями Keycloak | `http://localhost:8081/admin/`                                                            |
| Client ID портала                  | `service-desk-test`, публичный клиент                                                     |
| Callback портала                   | `http://localhost:8080/auth/callback` (разработка: `http://localhost:4200/auth/callback`) |
| Client ID сервиса студентов        | `student-service`                                                                         |
| Тип клиента студентов              | Публичный, без client secret                                                              |
| Способ входа                       | Authorization Code + PKCE S256                                                            |
| Callback сервиса студентов         | `http://localhost:4300/auth/callback`                                                     |
| Scopes                             | `openid profile email`                                                                    |
| API Service Desk                   | `http://localhost:8080`                                                                   |
| Audience API                       | `service-desk`                                                                            |
| Роли API в токене                  | `resource_access["service-desk"].roles`                                                   |

Discovery публикует адреса входа, обмена кода на токены, JWKS и выхода. Клиент перенаправляет браузер в Identity и использует PKCE. Password flow и Direct Access Grants отключены: пароль пользователя в Service Desk не передаётся.

`localhost` — машина, на которой работает браузер или клиент. Для внешнего доступа нужны HTTPS, собственные адреса issuer/API и зарегистрированные callback/origin. Новый `redirect_uri` автоматически не разрешается. Роли `student-service` относятся к сервису студентов; доступ к Service Desk определяют роли клиента `service-desk`.

[Swagger](swagger.md) использует отдельный публичный клиент `service-desk-swagger`. **Authorize** запускает вход и использует открытую SSO-сессию без повторного пароля. **Logout** очищает авторизацию Swagger и завершает общую сессию Identity. При известном конфликте `different_user_authenticated` вход продолжается с текущей SSO-сессией; неверный пароль и отсутствие прав не обходятся.

## Первичная настройка

Общий `bootstrap --apply` вызывает настройку автоматически. При ручном запуске после готовности Identity используется команда:

```sh
node --env-file=.env tools/configure-identity.mjs
```

Она создаёт профиль с административным атрибутом `team_slug`, синхронизирует пользователей LDAP и задаёт начальные роли. Одноразовые маркеры сохраняют последующие изменения пользователей, паролей и членства в группах. Swagger-клиент и серверный клиент каталога сотрудников согласуются при каждом запуске.

Секреты читаются из `.env` и не печатаются. Обмен пароля администратора через `admin-cli` выполняет только этот инструмент подготовки. Публичные клиенты портала и студентов используют Code + PKCE.

## Пользователи и права

Вход в административную консоль Keycloak: `administrator` в realm `master`, пароль `IDENTITY_ADMIN_PASSWORD`. Данные администратора студентам не передаются.

В realm `training` пользователь получает пароль в разделе **Credentials**, атрибут `team_slug` (для начального Service Desk — `demo`) и членство в группе:

| Группа               | Роль клиента `service-desk`         | Доступ                                                                           |
| -------------------- | ----------------------------------- | -------------------------------------------------------------------------------- |
| `desk-customers`     | `customer`                          | Свои обращения, публичная переписка, закрытие своего обращения                   |
| `desk-support`       | `support`                           | Обращения своего Service Desk, рабочие статусы, исполнители и внутренние заметки |
| `desk-support-leads` | `support-lead`, наследует `support` | Права поддержки и первоначальное назначение новых обращений                      |
| `desk-admins`        | `admin`                             | Права поддержки и все настройки Service Desk                                     |

LDAP federation с записью сохраняет пользователя и пароль в LDAP; править LDIF для обычного создания учётной записи не требуется. `team_slug` отображается на LDAP `employeeType`, попадает в JWT и меняется только администратором. Указанный раздел Service Desk должен существовать и быть активным: создание пользователя само по себе раздел не создаёт.

Группы наследуют роли клиента `service-desk`; прямые назначения также влияют на права. `GET /api/me` возвращает текущего пользователя, эффективную роль и `teamId`, без токенов и паролей. Учётная запись без роли Service Desk получает `403`. Роли проверяются после проверки подписи JWT.

Администратор Keycloak и администратор службы поддержки имеют разные полномочия. `administrator` управляет Identity; `desk-admin` работает в realm `training` с ролью `service-desk:admin`. Роли `student-service:user/moderator` не дают доступа к Service Desk API.

Группы и учётку `desk-admin` создаёт одноразовое обновление с маркером `training.access-model.version=1`. Начальные прямые назначения `alice` и `support` перенесены в группы. Повторный запуск сохраняет решения администратора: не возвращает снятое членство и не сбрасывает пароли. Автоматического создания нового раздела Service Desk и всех связанных учётных записей одной командой нет.

## Готовые учётные записи

| Логин          | Пароль                               | Назначение                                                        |
| -------------- | ------------------------------------ | ----------------------------------------------------------------- |
| `alice`        | `LDAP_ALICE_PASSWORD`                | Заявитель                                                         |
| `support`      | `LDAP_SUPPORT_PASSWORD`              | Сотрудник поддержки                                               |
| `support-lead` | `SUPPORT_LEAD_PASSWORD`              | Руководитель поддержки                                            |
| `desk-admin`   | `DESK_ADMIN_PASSWORD`                | Администратор службы поддержки                                    |
| `denied`       | `LDAP_DENIED_PASSWORD`               | Identity подтверждает личность, Service Desk отказывает в доступе |
| `disabled`     | Рабочего пароля в начальном LDAP нет | Проверка отказа при входе                                         |

Все переменные находятся в локальной `.env`; значения паролей в репозитории отсутствуют. После первой инициализации LDAP изменение `.env` не меняет сохранённый пароль. Для смены пароля используется раздел Credentials в Keycloak; тома и БД сохраняются.

## Исполнители и руководитель поддержки

Новое обращение назначается единственному активному пользователю с эффективной ролью `support-lead` и тем же `team_slug`. При отсутствии руководителя или нескольких кандидатах создание возвращает `503` без записи обращения. Начальная учётка — `support-lead`; роль наследует `support` и назначается группой `desk-support-leads`.

Каталог читает серверный клиент `service-desk-directory` с правами `view-users`, `query-users`, `view-clients`. Он использует client credentials; секрет `IDENTITY_DIRECTORY_CLIENT_SECRET` хранится только на сервере. Пароль администратора Keycloak для работы каталога не используется. Кандидаты и роли перечитываются при назначении; предыдущий вход в Service Desk не требуется.

В портале имя исполнителя доступно только для просмотра. Студенческий сервис распределяет обращения через GET кандидатов и PUT назначения. При закрытии обращения исполнитель снимается вместе с изменением статуса; событие `jira:issue_updated` содержит `issue.fields.assignee=null`.

## Проверка access token

| Claim                                | Проверка или назначение                                        |
| ------------------------------------ | -------------------------------------------------------------- |
| `iss`                                | Точное совпадение с настроенным issuer                         |
| `aud`                                | Содержит `service-desk`                                        |
| `exp`, `iat`                         | Обязательные поля; `exp` ограничивает срок действия            |
| `nbf`                                | Проверяется, если присутствует                                 |
| `typ`                                | В теле access token имеет значение `Bearer`                    |
| `sub`                                | Обязательный идентификатор пользователя                        |
| `preferred_username`                 | Логин и авторство действий                                     |
| `team_slug`                          | Существующий активный раздел Service Desk                      |
| `resource_access.service-desk.roles` | Роли API; приоритет `admin`, затем `support`, затем `customer` |

API принимает **access token** в `Authorization: Bearer`, проверяет RS256-подпись по JWKS через `jose`, issuer, audience и время действия. ID token и client secret не заменяют access token. `support-lead` наследует `support`, поэтому API допускает руководителя как сотрудника поддержки.

Портал получает параметры входа из `GET /api/config`, запускает `keycloak-js` с `login-required` и отправляет Bearer в свой API. `/auth/callback` — клиентский маршрут SDK. Access/refresh tokens остаются в памяти SDK; в localStorage/sessionStorage они не сохраняются.

Изменение пароля или роли не переписывает уже выданный JWT. Новые права отражаются в новом токене; прежний может действовать до истечения срока. Немедленного отзыва каждого запроса через introspection нет. Активность раздела Service Desk проверяется при обращении к API.

Ответы: `401` — недействительный токен, `403` — нет роли или доступа к разделу, `503` — недоступен сервис проверки ключей. При ошибке проверки API не выдаёт тестового пользователя и не отключает проверку подписи.

## Конфигурация и повторный запуск

Шаблон realm: `apps/identity/realm/training-realm.json`. Identity использует схему `identity` в общей БД `training`. Команды отдельных приложений используют тот же Compose-проект и общие зависимости:

```sh
docker compose up --build -d --wait identity
docker compose up --build -d --wait service-desk
```

Общий `docker compose up --build -d --wait` запускает пять сервисов. Импорт создаёт realm в пустой БД. Для существующего realm правка шаблона не обновляет клиентов автоматически: callback, mapper и federation меняются административной операцией или соответствующим инструментом подготовки. Постоянные тома сохраняются.

| Параметр                      | Назначение                                                |
| ----------------------------- | --------------------------------------------------------- |
| `OIDC_ISSUER_URL`             | Публичный issuer, совпадающий с `iss` и discovery         |
| `OIDC_INTERNAL_ISSUER_URL`    | Внутренний адрес для запросов сервера к Identity в Docker |
| `identity.audience`           | Audience и имя клиента ролей; по умолчанию `service-desk` |
| `identity.allowInsecureLocal` | Локальный HTTP только в режиме разработки                 |
| `BASE_URL`                    | Внешний адрес API для ссылок                              |

Для проверки JWT серверу достаточно публичных issuer, audience и JWKS. Отдельный секрет нужен только клиенту каталога сотрудников. Внутренний маршрут Docker не меняет issuer токенов и адрес браузерного входа; проверка TLS сохраняется.

## Создание обращения и уведомления

Пример использует access token заявителя; совместимый статический токен работает только при явно включённом legacy-режиме:

```sh
curl -X POST http://localhost:8080/rest/servicedeskapi/request \
    -H "Authorization: Bearer $ACCESS_TOKEN" \
    -H 'Content-Type: application/json' \
    -d '{"serviceDeskId":"3","requestTypeId":"10001","requestFieldValues":{"customfield_12900":"TRAINING-PC-01","description":"Нужна замена устройства","customfield_20001":{"id":"20002"},"customfield_20002":{"id":"20101"}}}'
```

Поля формы возвращает `GET /rest/servicedeskapi/servicedesk/3/requesttype/10001/field`. Успех создания — `201`. Обращение, история и `jira:issue_created` записываются одной транзакцией. Тип `10001` и его значения — конфигурация стенда, не подтверждённая корпоративная форма.

Администратор задаёт адрес уведомлений через [настройки Service Desk](settings.md). Получатель проверяет `X-Training-Signature: sha256=<hex>` от исходных байтов тела и исключает повторы по `X-Training-Event-Id`. Ему передаётся отдельный ключ подписи, мастер-секрет остаётся на сервере.

Ответ `201` не подтверждает доставку. Для проверки нужен зарегистрированный доступный публичный HTTPS-получатель; локальные и внутренние адреса запрещены. Список обращений с пагинацией помогает сверять пропущенные события. Формат и ограничения — в [контракте API](api-compatibility.md).

## Совместимые статические токены

`TEAM_API_TOKEN` и `CUSTOMER_API_TOKEN` по умолчанию отключены настройкой `security.allowLegacyApiTokens=false`. Их можно включить общей настройкой с перезапуском; штатный доступ использует JWT Identity. В БД хранятся хеши токенов с ролью и разделом Service Desk. `ADMIN_TOKEN` сохраняет административный доступ для подготовки контура. Эти токены не создают сессию Identity и не управляют пользователями Keycloak; студентам административные секреты не передаются.

Локальные HTTP и LDAP предназначены для разработки. Для внешнего доступа нужны HTTPS, защищённый LDAP, управление секретами и резервное копирование. Локальная установка не меняет корпоративные LDAP/ADFS, DNS и не публикует стенд на VPS.

Демонстрационный логин сотрудника — `support`, пароль задаёт `LDAP_SUPPORT_PASSWORD`. При обновлении прежний логин переименовывается с сохранением ID, пароля и членства в группах. Технический ключ роли — `support`.

Для обновления существующей `.env` команда `node tools/setup-env.mjs --extend` переносит `LDAP_AGENT_PASSWORD` в `LDAP_SUPPORT_PASSWORD` с тем же значением. Различающиеся значения двух ключей требуют ручного выбора действующего пароля; новый случайный пароль поверх существующего не генерируется.

При обновлении роль и группа переименовываются в Keycloak с сохранением ID и назначений: актуальная роль — `support`, группа — `desk-support`. После обновления требуется новый access token.
