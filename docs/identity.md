# Identity: устройство и обслуживание

Документ предназначен разработчику и владельцу развёртывания. Создание пользователей, роли и подключение приложения описаны в студенческих инструкциях: [Keycloak](students/01-keycloak-and-roles.md) и [OpenID Connect](students/02-openid-connect.md).

## Где хранятся данные

Keycloak использует схему `identity` общей БД `training`. Пользователи, пароли и атрибут службы находятся в LDAP. Writable federation позволяет создавать учётки и менять пароли через Keycloak Admin Console.

Service Desk проверяет access token по JWKS. Он не получает пароль пользователя, не выполняет LDAP bind при каждом запросе и не создаёт собственную серверную сессию входа.

## Клиенты realm training

| Client ID                | Назначение                            | Способ работы                    |
| ------------------------ | ------------------------------------- | -------------------------------- |
| `service-desk`           | Ресурс API, audience и роли           | Bearer-only                      |
| `service-desk-test`      | Встроенный портал                     | Public, Code + PKCE S256         |
| `service-desk-swagger`   | Swagger UI                            | Public, Code + PKCE S256         |
| `student-service`        | Приложение студентов                  | Public, Code + PKCE S256         |
| `service-desk-directory` | Серверное чтение каталога сотрудников | Confidential, client credentials |

Для браузерных клиентов password grant и implicit flow отключены. Секрет каталога хранится в `IDENTITY_DIRECTORY_CLIENT_SECRET`; его права — `view-users`, `query-users`, `view-clients`. Он не предназначен для приложения студентов и не заменяет его учётку.

У портала callback `/auth/callback` — клиентский маршрут SDK. Адреса по умолчанию: `http://localhost:8080/auth/callback` и `http://localhost:4200/auth/callback`. У `student-service` — `http://localhost:4300/auth/callback`. Другие адреса регистрируются явно.

## Подготовка и повторный запуск

`bootstrap --apply` вызывает настройку после готовности Keycloak. При ручном запуске используется:

```sh
node --env-file=.env tools/configure-identity.mjs
```

Подготовка задаёт профиль с административным `team_slug`, синхронизирует LDAP и создаёт начальные группы/учётки. Одноразовые маркеры защищают последующие изменения пользователей, паролей и ролей от сброса. Клиенты Swagger и каталога согласуются отдельно при повторных запусках.

Настройка также выполняет совместимые обновления логина сотрудника, роли `support` и группы `desk-support`. При переименовании сохраняются идентификаторы Keycloak, членство и назначения. Конфликт занятых имён останавливает обновление.

`apps/identity/realm/training-realm.json` импортируется в пустую БД Identity. Изменение файла или ENV не обновляет уже существующий realm. Для действующего стенда настройки меняются административной операцией, без удаления томов.

Уже созданный пароль LDAP не меняется от редактирования `.env`. Для его смены используется Credentials в Keycloak. `tools/setup-env.mjs --extend` добавляет недостающие переменные и переносит прежнее имя переменной пароля сотрудника с сохранением значения.

## Связь пользователя со службой

`team_slug` отображается на LDAP `employeeType`; редактировать его может администратор. При запросе Service Desk ищет активную службу с этим slug и получает её `teamId`. Пользовательское поле тела запроса не расширяет доступ.

Роли API — `customer`, `support`, `admin` клиента `service-desk`. `support-lead` включает `support`. При нескольких ролях эффективная роль API выбирается в порядке `admin`, `support`, `customer`; поэтому `/api/me` может показать руководителю `support`.

Для создания обращения каталог должен вернуть ровно одного включённого руководителя с тем же `team_slug`. Отсутствие или несколько руководителей, как и сбой каталога, дают `503` без частичной записи обращения. Кандидаты для переназначения перечитываются из Identity: вход кандидата в Service Desk заранее не требуется.

## Проверка токенов

Backend проверяет RS256-подпись, точный `iss`, audience `service-desk`, обязательные `sub`, `iat`, `exp`, значение payload `typ=Bearer` и `nbf`, если оно есть. Затем проверяются логин, `team_slug`, роли и активность службы.

Права берутся из `resource_access.service-desk.roles`. Роли другого клиента и неподписанные данные браузера не дают доступа. Собственные роли/audience сервиса студентов настраиваются отдельно по второй инструкции.

Недействительный токен даёт `401`, отсутствие прав или активной службы — `403`, недоступность проверки ключей — `503`. Назначение новой роли не переписывает старый JWT; нужен новый токен. Уже выданный access token может приниматься до срока истечения после logout: introspection на каждый запрос не выполняется.

## Swagger и общий вход

Swagger доступен на `/docs/`, OpenAPI — `/docs/json`. Authorize открывает стандартную форму Identity, получает токен через Code + PKCE и автоматически подставляет его в запросы. Авторизация хранится в памяти страницы, без persistAuthorization.

Callback Swagger — `/docs/static/oauth2-redirect.html`, адрес возврата после выхода — `/docs/`. Точные origins/callbacks берутся из `DOCKER_BASE_URL` и `API_DOCS_DEV_URL` при настройке клиента.

Logout в окне авторизации сначала очищает токен Swagger, затем завершает SSO-сессию Keycloak. При известном конфликте вкладок форма продолжает вход через текущую сессию; пароль и права не обходятся. Автоматический переход ограничен одной попыткой и доверенным restart URL Keycloak.

## Публичный адрес и внутренний транспорт

| Настройка                      | Назначение                                            |
| ------------------------------ | ----------------------------------------------------- |
| `IDENTITY_PUBLIC_URL`          | Адрес Identity для браузера                           |
| `OIDC_ISSUER_URL`              | Публичный issuer, совпадающий с `iss`                 |
| `OIDC_INTERNAL_ISSUER_URL`     | Внутренний маршрут discovery/JWKS и каталога в Docker |
| `BASE_URL` / `DOCKER_BASE_URL` | Адрес Service Desk в соответствующем режиме           |

Внутренний транспорт не меняет `iss` токена и браузерные адреса. Локальный HTTP разрешён только явно вне production. Внешнее развёртывание требует HTTPS и согласованных hostname/callback/origin. Проверка TLS не отключается для обхода ошибки настройки.
