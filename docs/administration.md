# Управление Service Desk

Контур состоит из Identity, LDAP, Service Desk и общего PostgreSQL. Пользователи и права настраиваются в [Keycloak](http://localhost:8081/admin/), параметры сервиса — через [GET/PUT/PATCH /api/settings](settings.md).

## Учётные записи и права

В realm `training` создайте пользователя, задайте пароль и административный атрибут `team_slug=demo`. Затем добавьте его в одну из групп:

| Группа               | Права                                                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| `desk-customers`     | Заявитель: создаёт и читает свои обращения, пишет публичные сообщения                                      |
| `desk-support`       | Сотрудник поддержки: обрабатывает обращения своего Service Desk, меняет статусы и пишет внутренние заметки |
| `desk-support-leads` | Руководитель поддержки: первоначальный исполнитель новых обращений, права сотрудника поддержки             |
| `desk-admins`        | Администратор службы поддержки: возможности поддержки и изменение всех настроек сервиса                    |

Внутренние ключи ролей Keycloak: `customer`, `support`, `admin` клиента `service-desk`. Для проверки прав используйте `GET /api/me`; наличие метода в Swagger не означает наличие права его вызвать. Перед сменой пользователя нажмите Logout.

Готовые учётки: `alice` — заявитель, `support` — сотрудник поддержки, `desk-admin` — администратор службы поддержки, `denied` — без доступа к Service Desk. Пароли в `.env`; пароль администратора приложения — `DESK_ADMIN_PASSWORD`. `administrator` в realm `master` управляет Keycloak и не заменяет администратора приложения.

## Подключение сервиса студентов

Передайте issuer, публичный клиент `student-service`, зарегистрированный callback и свои учётные данные по [инструкции Identity](identity.md). Приложение студентов находится в отдельном репозитории. Пользователь создаёт обращение в нашем портале; Service Desk сохраняет обращение и отправляет уведомление на настроенный адрес.

Войдите как администратор, получите `GET /api/settings`, задайте адрес уведомлений в `teams[teamId].webhook` и сохраните весь JSON через PUT. Текущий `teamId` показывает `GET /api/me`. Получателю передаётся отдельный ключ подписи, а не мастер-секрет; `tools/webhook-key.mjs --team-id UUID` предназначен для преподавателя и выводит чувствительное значение. Не запускайте его без запроса на выдачу ключа.

Отдельных ручек создания команд, выдачи статических токенов и SQL-подписок нет. Базовый Service Desk `demo` создаётся при начальной подготовке. Настройка дополнительных изолированных Service Desk требует отдельного сценария подготовки данных; создание произвольного `team_slug` в Keycloak само по себе такой раздел не создаёт.

## Состояние и запуск

Данные обращений и Identity хранятся в одной БД `training` с разными схемами; пароли пользователей — в LDAP. При повторном запуске ENV, роли, JSON настроек и тома сохраняются. Команды запуска и резервные копии — в [запуск через Docker](docker.md).

## Первоначальный исполнитель

Для каждого Service Desk задайте ровно одного включённого пользователя с ролью клиента `support-lead` (группа `desk-support-leads`, наследует права поддержки). В demo это `support-lead`, пароль `SUPPORT_LEAD_PASSWORD` в `.env`. Bootstrap создаёт его один раз, последующие изменения ролей и пароля администратором не сбрасываются. Новые обращения сразу назначаются этому пользователю. Старые обращения автоматически не переназначаются.

В портале исполнитель показан только для просмотра. Студенты реализуют своё распределение и при необходимости вызывают GET assignable/search и PUT assignee. При закрытии обращения основной исполнитель снимается автоматически.

Сервер читает каталог через отдельный конфиденциальный клиент `service-desk-directory` с правами только `view-users`, `query-users`, `view-clients`. Его секрет `IDENTITY_DIRECTORY_CLIENT_SECRET` хранится в ENV сервера, не выдаётся браузеру или студентам; пароли администратора Keycloak во время работы не используются. Управление пользователями и ролями остаётся в Keycloak.
