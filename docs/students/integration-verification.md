# Проверка инструкции на работающем стенде

Проверка выполнена 8 ноября 2026 года с обычного компьютера разработчика. Keycloak и Service Desk работали на `auth.makar-star.space` и `desk.makar-star.space`; приложение, proxy и приёмник webhook — локально. Исходники и база сервера для клиентских сценариев не использовались. Для временной настройки ролей и создания пользователя использовался административный API Keycloak.

## Что проверено

| Сценарий                                                                                 | Результат                                                                                                                      |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Вход существующих `alice`, `support`, `desk-admin` через public client `student-service` | Настоящий Authorization Code + PKCE S256: код, state, nonce, подпись ID token; callback `http://localhost:4300/auth/callback`  |
| Backend из второй инструкции с временно настроенными ролью и audience `student-service`  | HTTP `200` для `desk-admin`, `403` для `support` и `alice`, `401` без токена и с неверным токеном                              |
| Создание пользователя через Keycloak                                                     | Новая учётка связана с LDAP; пароль, группа `desk-customers`, вход по PKCE и `GET /api/me` с ролью `customer` проверены        |
| Настройки Service Desk под разными учётками                                              | `desk-admin`: `200`; `support` и `alice`: `403`; запрос без токена: `401`                                                      |
| Настройка получателя                                                                     | Настоящий PATCH `/api/settings` с ETag/If-Match, новая revision, URL применяется без рестарта                                  |
| Локальный proxy                                                                          | Реальный Vite на порту `4300` переслал Authorization в Service Desk; без токена вернул `401`; `/auth/callback` отдал SPA       |
| Поля, создание и список                                                                  | Метаданные формы `3/10001` доступны; создание вернуло `201`, заявка появилась в списке                                         |
| Первоначальный исполнитель                                                               | Новая заявка назначена `support-lead`                                                                                          |
| Назначение через API                                                                     | Поддержка получила кандидатов и назначила `support` с ответом `204`; заявителю в назначении отказано с `403`                   |
| Переписка                                                                                | Публичный и внутренний комментарии созданы с `201`; заявитель видит только публичный                                           |
| Статусы                                                                                  | Разрешённые переходы получены GET; переходы `10006` и `10008` выполнены с `204`                                                |
| Закрытие заявителем                                                                      | Переход `10011` с решением `10100` выполнен с `204`; исполнитель стал `null` в карточке и webhook                              |
| Реальный webhook                                                                         | Worker Service Desk доставил на localhost семь подписанных событий заявки `HELP-5` через HTTPS Quick Tunnel                    |
| Готовый приёмник из третьей инструкции                                                   | Сохранил реальные события создания и закрытия `HELP-6`; повторный ID не записался второй раз, неверная HMAC-подпись дала `401` |
| Обновление токена и logout                                                               | Refresh работал до завершения сессии; после logout тот же refresh получил `400`                                                |

Приёмник из инструкции — демонстрационный: сохраняет события в локальный файл. В приложении команды необходимы собственная БД и обработка событий. Входящее событие сообщает об изменении, актуальная карточка читается через API.

## Состояние после проверки

Временная учётка удалена; её отсутствие проверено повторным поиском. Временная роль `student-service:admin`, её назначение и audience mapper удалены; исходные mapper и набор ролей клиента сверены. Участники продолжают работать с прежними пользователями и ролями.

Поэтому на текущем стенде перед проверкой собственного admin-only backend нужны шаги создания роли и audience из первой инструкции. Готового назначения этой роли всем администраторам Service Desk нет.

Адрес временного туннеля сохранён как пример в настройках. Получатель отключён через PATCH (`enabled=false`), туннель и локальные серверы остановлены. Перед своим тестом команда запускает приёмник и туннель, меняет URL и включает получателя. Мастер-секрет сервера в приёмник не передаётся: используется отдельный выданный ключ службы.

Тестовые обращения остаются в истории стенда. `HELP-5` и `HELP-6` закрыты. База, постоянные тома и чужие обращения не удалялись.

## Что проверено отдельно от браузера

Проверены HTTP/OIDC-запросы, реальные токены, backend из инструкции, Vite proxy, webhook и ответы API. Управление браузером не использовалось. Переходы по меню Keycloak и кнопки Swagger описаны по контракту и текущему интерфейсу; пошаговый ручной прогон всех экранов ещё не выполнялся.

Настоящий сервер команды на другом домене не разворачивался. Его callback/origin/logout и публичный URL webhook регистрируются по тем же инструкциям; окончательная проверка проводится после публикации приложения команды.

В локальном коде добавлено отображение необязательного `if-match` в Swagger для PUT/PATCH настроек. Контракт приёма заголовка уже проверен на стенде; новое поле интерфейса появится после деплоя этой правки. В третьей инструкции указан вариант первого PATCH без этого поля для прежней версии Swagger.

## Повторный прогон владельцем стенда

В репозитории сохранён `tools/student-integration-smoke.mjs`. Запуск с `--apply` создаёт и закрывает одно новое обращение, меняет получателя webhook и проверяет доставку на localhost. Скрипт не создаёт пользователей и не меняет роли Keycloak. Обычной команде студентов этот инструмент и доступ к репозиторию не требуются.

Для оператора нужен Node.js 22, установленные зависимости проекта, свободные порты `4300` и `4310`, запущенный HTTPS-туннель к `localhost:4310` и отдельный игнорируемый файл ENV с параметрами:

```dotenv
IDENTITY_PUBLIC_URL=https://auth.makar-star.space
DOCKER_BASE_URL=https://desk.makar-star.space
STUDENT_REDIRECT_URI=http://localhost:4300/auth/callback
LDAP_ALICE_PASSWORD=пароль_заявителя
LDAP_SUPPORT_PASSWORD=пароль_поддержки
DESK_ADMIN_PASSWORD=пароль_администратора_Service_Desk
STUDENT_WEBHOOK_URL=https://hostname_вашего_туннеля/webhooks/service-desk
STUDENT_WEBHOOK_SECRET=выданный_ключ_службы
```

```sh
node --env-file=.env.student-smoke tools/student-integration-smoke.mjs --apply
```

После прогона получатель отключается через Swagger, затем туннель останавливается. Повторный прогон создаёт новое обращение; это проверка с изменением учебных данных. Роль своего backend и управление учётками проверены отдельно от этого скрипта.
