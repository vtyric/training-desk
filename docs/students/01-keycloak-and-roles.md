# 1. Keycloak: пользователи и роли

После этой инструкции в Keycloak будет пользователь, которому разрешён доступ к Service Desk и, при необходимости, административному разделу приложения команды.

## 1. Вход в консоль

1. Открывается [консоль Keycloak](https://auth.makar-star.space/admin/master/console/#/training/users).
2. Вводится логин `administrator` и выданный пароль администратора Keycloak.
3. В списке realm выбирается **training**. Его отображаемое название — **Artsofte Federation**.
4. Слева открывается **Users**.
5. В **Search user** вводится `*`, затем нажимается стрелка справа.

Ожидаемый результат — список пользователей, включая `alice`, `support`, `support-lead` и `desk-admin`. При LDAP federation Keycloak не загружает весь каталог автоматически: пустая страница до поиска не означает отсутствие пользователей.

`administrator` находится в realm `master`. Для его входа используется адрес `/admin/master/console/`. Адреса `/login-actions/authenticate?...` — временные шаги входа; их не сохраняют как ссылку в закладки. Если уже открыта ошибочная сессия, используется выход и повторный вход через ссылку выше.

## 2. Какие учётки уже подготовлены

| Логин          | Для чего используется                       | Права клиента `service-desk`        |
| -------------- | ------------------------------------------- | ----------------------------------- |
| `alice`        | Создать, прочитать и закрыть своё обращение | `customer`                          |
| `support`      | Обрабатывать обращения службы               | `support`                           |
| `support-lead` | Первоначальный исполнитель новых обращений  | `support-lead`, наследует `support` |
| `desk-admin`   | Менять настройки Service Desk               | `admin`                             |
| `denied`       | Проверить отказ API после успешного входа   | Нет ролей Service Desk              |

Это роли приложения, а не права управления консолью Keycloak. `administrator` управляет Keycloak, `desk-admin` — настройками Service Desk через Swagger.

Для первых проверок можно использовать эти учётки с выданными паролями. Для участников команды создаются отдельные пользователи.

## 3. Создание пользователя

1. В **Users** нажимается **Add user**.
2. Задаются **Username**, **First name** и **Last name**. Например: `ivan.petrov`, `Иван`, `Петров`.
3. Поле **team_slug** заполняется значением `demo`. Это идентификатор подготовленной службы, а не имя пользователя.
4. Нажимается **Create**. Пользователь должен быть включён: **Enabled**.
5. В карточке открывается **Credentials → Set password**. Задаётся пароль. Для первого теста **Temporary** выключается, затем изменение сохраняется.
6. Во вкладке **Groups** нажимается **Join group**, выбирается одна из групп ниже и подтверждается вступление.

| Группа               | Что разрешает                                                                           |
| -------------------- | --------------------------------------------------------------------------------------- |
| `desk-customers`     | Создание и просмотр своих обращений, публичные комментарии, закрытие своего обращения   |
| `desk-support`       | Просмотр обращений службы, назначение исполнителя, рабочие статусы и внутренние заметки |
| `desk-admins`        | Права поддержки и GET/PUT/PATCH `/api/settings`                                         |
| `desk-support-leads` | Права поддержки и первоначальное назначение новых обращений                             |

В службе нужен ровно один активный руководитель. Для обычного участника группы `desk-support` достаточно; добавлять второго руководителя не требуется. Если руководителей нет или их несколько, создание обращения вернёт `503`.

Учётная запись сохраняется через Keycloak в подключённый LDAP. Отдельно добавлять запись в LDAP не требуется. Значение `team_slug=team-1` само по себе новую службу не создаст: неподготовленное значение приведёт к отказу Service Desk.

Если `team_slug` не отображается, проверяется **Realm settings → User profile**. В конфигурации стенда атрибут уже должен быть доступен администратору.

## 4. Где назначать роли напрямую

1. **Users → нужный пользователь → Role mapping → Assign role**.
2. В фильтре выбирается **Filter by clients**.
3. Находится клиент **service-desk**, затем нужная роль: `customer`, `support` или `admin`.
4. Роль отмечается и подтверждается кнопкой **Assign**.

Группы из предыдущего шага уже назначают соответствующие роли. Прямое назначение нужно, когда выбран такой способ управления доступом. При удалении пользователя из группы прямые роли сохраняются; проверяются **Effective roles** и все источники назначения.

## 5. Доступ в своё приложение только администраторам

Для этого используется клиент **student-service**. Роли `service-desk` управляют внешним API, роли `student-service` — приложением команды.

В исходной конфигурации `student-service` есть роли `user` и `moderator`. Роль `admin` и audience собственного backend нужно подготовить по шагам ниже. Один успешный вход через Keycloak не ограничивает приложение администраторами — проверку роли выполняет backend команды.

### Создание и назначение `student-service:admin`

1. **Clients → student-service → Roles → Create role**.
2. В **Role name** вводится `admin`, затем **Save**.
3. **Users → пользователь, которому разрешён вход → Role mapping → Assign role → Filter by clients**.
4. Выбирается роль `admin` клиента **student-service**, затем **Assign**.

Для теста роль можно назначить `desk-admin`. Обычным `alice` и `support` она не назначается: это позволит проверить отказ собственного backend.

### Добавление audience собственного backend

1. **Clients → student-service → Client scopes**.
2. Открывается dedicated scope **student-service-dedicated**, затем **Mappers → Configure a new mapper**.
3. Выбирается тип **Audience**.
4. Задаются **Name = Student service audience**, **Included Client Audience = student-service**, **Add to access token = On**, затем **Save**.

Mapper **Service Desk audience** сохраняется: он добавляет `service-desk`, который нужен внешнему API. Новый mapper добавляет второе назначение токена — `student-service`.

### Проверка ролей в access token

В **Clients → student-service → Client scopes → Evaluate** выбирается пользователь, затем просматривается **Generated access token**. После обычного входа тот же результат можно проверить локально, декодировав токен в инструментах своего приложения. Токен не пересылается на внешние сайты.

У администратора приложения ожидаются:

```json
{
    "iss": "https://auth.makar-star.space/realms/training",
    "aud": ["service-desk", "student-service"],
    "team_slug": "demo",
    "resource_access": {
        "service-desk": { "roles": ["admin"] },
        "student-service": { "roles": ["admin"] }
    }
}
```

В `aud` и `resource_access` могут быть дополнительные значения. Важны наличие двух указанных audience и нужной роли своего клиента.

Если роли `student-service` нет в токене, в dedicated scope добавляется mapper **User Client Role**:

| Поле                | Значение                                |
| ------------------- | --------------------------------------- |
| Name                | `Student service roles`                 |
| Client ID           | `student-service`                       |
| Token Claim Name    | `resource_access.student-service.roles` |
| Claim JSON Type     | `String`                                |
| Multivalued         | On                                      |
| Add to access token | On                                      |

Если роль уже передаёт стандартный scope `roles`, второй mapper не нужен. При отключённом **Full scope allowed** в scope клиента отдельно разрешаются нужные роли. Результат снова проверяется через Evaluate.

## 6. Проверка результата

После изменения ролей выполняется выход и повторный вход: уже выданный JWT не изменяется.

| Проверка                                                                | Ожидаемый результат |
| ----------------------------------------------------------------------- | ------------------- |
| `desk-admin` с `student-service:admin` открывает защищённое API команды | `200`               |
| `alice` или `support` без `student-service:admin` вызывают это API      | `403`               |
| Запрос без access token                                                 | `401`               |
| `desk-admin` вызывает `/api/settings` Service Desk                      | `200`               |
| `support` вызывает `/api/settings` Service Desk                         | `403`               |

Проверка подписи токена и роли на backend приведена во [второй инструкции](02-openid-connect.md). Скрытая кнопка в браузере не заменяет эту проверку.

Для управления realm другим участником можно назначить ему `realm-management:realm-admin` в **Role mapping**. Это отдельное административное право; оно не требуется обычному сотруднику поддержки и не заменяет роли `service-desk` или `student-service`.

Официальная справка: [пользователи, роли и scopes Keycloak](https://www.keycloak.org/docs/latest/server_admin/).
