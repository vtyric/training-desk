# 1. Пользователи и роли Keycloak

Эта инструкция предназначена студентам — администраторам выданного стенда. После настройки пользователи входят под своими учётками, получают роли в токене и выполняют разрешённые действия в Service Desk и приложении команды.

## Два административных доступа

| Доступ                    | Для чего нужен                                                      |
| ------------------------- | ------------------------------------------------------------------- |
| Администратор Keycloak    | Пользователи, клиенты, группы и роли в разрешённом realm            |
| Роль `service-desk:admin` | Чтение и изменение JSON настроек Service Desk через `/api/settings` |

Адрес консоли realm приложения: `https://auth.example.ru/admin/training/console/`. Если выдан начальный администратор `master`, вход выполняется через `/admin/`, затем выбирается `training`. В текущем контуре начальный логин — `administrator`; пароль передаётся отдельно.

Для второго администратора команды создаётся отдельная учётка в `training`. В **Role mapping → Assign role → Filter by clients** ей назначается `realm-management:realm-admin`. Это управление данным realm. Для изменения настроек Service Desk ей отдельно нужна группа `desk-admins`.

Административные учётки используются для настройки стенда. Проверка сценария заявителя выполняется под пользователем с ролью `customer`.

## Какие права проверяет Service Desk

Роли находятся в **Clients → service-desk → Roles**:

| Роль           | Название                       | Права                                                                                         |
| -------------- | ------------------------------ | --------------------------------------------------------------------------------------------- |
| `customer`     | Заявитель                      | Создание и просмотр своих обращений, публичная переписка, закрытие своего открытого обращения |
| `support`      | Сотрудник поддержки            | Обращения своей службы, рабочие статусы, внутренние заметки, поиск и назначение исполнителей  |
| `support-lead` | Руководитель поддержки         | Наследует `support`; первоначальный исполнитель новых обращений                               |
| `admin`        | Администратор службы поддержки | Права поддержки и GET/PUT/PATCH `/api/settings`                                               |

Готовые группы назначают эти роли пользователям:

| Группа               | Роль клиента `service-desk`       |
| -------------------- | --------------------------------- |
| `desk-customers`     | `customer`                        |
| `desk-support`       | `support`                         |
| `desk-support-leads` | `support-lead`, включая `support` |
| `desk-admins`        | `admin`                           |

Для каждой службы нужен ровно один включённый пользователь с эффективной ролью `support-lead`. Новые обращения сначала назначаются ему. При отсутствии руководителя или нескольких кандидатах создание возвращает `503` без записи обращения. Дальнейшее распределение выполняет приложение команды; закрытие снимает исполнителя.

## Как создать пользователя

1. В консоли выбран realm **training**, раздел **Users → Add user**.
2. В **Username** задан логин, например `sergey.petrov`; в имени и фамилии — **Сергей Петров**. Логин содержит до 128 латинских букв, цифр и символов `.`, `_`, `-`, `@`. Отображаемое имя может быть русским.
3. Атрибут **team_slug** содержит идентификатор службы, например `demo`. Если поля нет, оно проверяется в **Realm settings → User profile**: атрибут должен быть виден и доступен для изменения администраторам. В шаблоне стенда он уже описан.
4. После сохранения учётка записывается в LDAP через writable federation Keycloak. Отдельная LDAP-запись вручную не создаётся.
5. В **Credentials → Set password** задан пароль. **Temporary = On** требует смены при первом входе; **Off** сохраняет постоянный пароль.
6. В **Groups → Join group** выбрана группа. Для сотрудника поддержки — `desk-support`.
7. Пользователь включён (**Enabled**); в **Role mapping → Effective roles** отображаются ожидаемые роли клиента `service-desk`.

Служба с заданным `team_slug` должна существовать и быть активной в Service Desk. В текущем стенде подготовлена `demo`. Значение `team-1` в Keycloak само по себе новую службу не создаёт и приведёт к `403`, если соответствующий раздел не подготовлен.

Эффективные права складываются из прямых назначений и групп. Если роль `support` выдана напрямую, удаление пользователя из `desk-support` её не снимет.

## Как задать права собственного приложения

Клиент **student-service** представляет приложение команды. В нём уже определены роли:

| Роль        | Пример использования командой       |
| ----------- | ----------------------------------- |
| `user`      | Просмотр разрешённых разделов       |
| `moderator` | Обработка и распределение обращений |

Проверку этих ролей реализует backend команды. Service Desk проверяет роли своего клиента `service-desk`.

Например, модератору `sergey.petrov` нужны:

- `team_slug=demo` и группа `desk-support` для рабочего API Service Desk;
- роль **student-service → moderator** для действий собственного приложения.

Собственная роль назначается через **Role mapping → Assign role → Filter by clients → student-service**.

### Проверка claims и настройка mapper

В **Clients → student-service → Client scopes → Evaluate** выбирается пользователь и проверяется access token. Если роли уже включены стандартными client scopes, дополнительный mapper не нужен.

При отсутствии собственных ролей в dedicated scope клиента добавляется mapper **User Client Role**:

| Поле                | Значение                                |
| ------------------- | --------------------------------------- |
| Client ID           | `student-service`                       |
| Token Claim Name    | `resource_access.student-service.roles` |
| Claim JSON Type     | `String`                                |
| Multivalued         | On                                      |
| Add to access token | On                                      |

Если отсутствует audience собственного backend, добавляется mapper **Audience** с **Included Client Audience = student-service** и **Add to access token = On**. Существующие mapper ролей и audience `service-desk` сохраняются: они нужны внешнему API.

Названия страниц консоли могут отличаться между версиями. Результат проверяется через Evaluate или новый токен после входа. Определение роли в Keycloak само по себе не гарантирует её наличие в токене.

Ожидаемый фрагмент claims после настройки:

```json
{
    "iss": "https://auth.example.ru/realms/training",
    "aud": ["service-desk", "student-service"],
    "preferred_username": "sergey.petrov",
    "name": "Сергей Петров",
    "team_slug": "demo",
    "resource_access": {
        "service-desk": { "roles": ["support"] },
        "student-service": { "roles": ["moderator"] }
    }
}
```

Это содержимое токена для примера. Декодирование позволяет его прочитать; право доступа backend выдаёт после проверки подписи и ограничений, описанной во [второй инструкции](02-openid-connect.md).

## Как проверить назначение роли

После изменения роли нужен новый токен: обновление через SDK либо выход и повторный вход. Уже выданный JWT не меняется.

```http
GET /api/me
Authorization: Bearer <ACCESS_TOKEN>
```

Service Desk возвращает `username`, эффективную `role`, русское `roleName` и `teamId`. Приоритет ролей — `admin`, затем `support`, затем `customer`. Руководитель наследует `support`, поэтому `/api/me` может вернуть ему `role: "support"`.

| Ситуация                             | Причина, которую нужно проверить                                         |
| ------------------------------------ | ------------------------------------------------------------------------ |
| Вход прошёл, API вернул `403`        | Роль именно клиента `service-desk`, `team_slug` и активность службы      |
| В токене нет `moderator`             | Назначение роли, mapper и ограничения role scope                         |
| После удаления группы права остались | Прямые назначения, другие группы или старый токен                        |
| Создание вернуло `503`               | Единственного активного руководителя своей службы и доступность каталога |

Далее: [вход через OpenID Connect в проекте команды](02-openid-connect.md).

Справка: [управление пользователями и ролями Keycloak](https://www.keycloak.org/docs/latest/server_admin/).
