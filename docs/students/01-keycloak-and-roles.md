# 1. Keycloak: пользователи и роли

Эта инструкция предназначена студентам — администраторам учебного стенда. Keycloak и Service Desk уже работают на сервере. Исходники стенда для настройки пользователей и клиентов не требуются.

Результат: пользователи входят под своими учётками, их роли появляются в токене, а Service Desk допускает только разрешённые действия.

## Адреса и доступ

В примерах используются адреса, которые нужно заменить на выданные адреса стенда:

| Сервис           | Пример публичного адреса         | В текущем локальном контуре    |
| ---------------- | -------------------------------- | ------------------------------ |
| Keycloak         | `https://auth.example.ru`        | `http://localhost:8081`        |
| Консоль Keycloak | `https://auth.example.ru/admin/` | `http://localhost:8081/admin/` |
| Service Desk     | `https://desk.example.ru`        | `http://localhost:8080`        |
| Realm приложения | `training`                       | `training`                     |

Для управления учётками нужен административный доступ к realm `training`. Адрес realm-консоли — `https://auth.example.ru/admin/training/console/`. Если выдан начальный администратор `master`, вход выполняется через `/admin/`, затем выбирается `training`. Организатор передаёт административный доступ отдельно от обычных учётных записей приложения. В текущем контуре начальный администратор Keycloak называется `administrator`; пароль в документ не включается.

Есть два разных административных доступа:

| Доступ                    | Что позволяет                                                      |
| ------------------------- | ------------------------------------------------------------------ |
| Администратор Keycloak    | Создаёт пользователей, клиентов, группы и роли в разрешённом realm |
| Роль `service-desk:admin` | Меняет JSON настроек Service Desk через `/api/settings`            |

Один доступ автоматически не выдаёт другой. Для настройки интеграции потребуются оба: доступ к консоли Keycloak и учётка приложения с ролью `service-desk:admin`.

## Доступ второго администратора команды

Если административная учётка уже выдана одному участнику, он может создать отдельную учётку для другого администратора. Пользователь создаётся в `training` по шагам ниже, затем в **Role mapping → Assign role → Filter by clients** получает `realm-management:realm-admin`. Это управление данным realm. Для входа используется `/admin/training/console/`.

Для изменения JSON Service Desk этой учётке отдельно назначается группа `desk-admins`. Административный доступ не используется в обычном сценарии заявителя: для него создаётся отдельная учётка `customer`.

## Роли Service Desk

Роли находятся в **Clients → service-desk → Roles**.

| Ключ роли      | Название                       | Права                                                                                                          |
| -------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `customer`     | Заявитель                      | Создание и просмотр своих обращений, публичная переписка, закрытие своего открытого обращения                  |
| `support`      | Сотрудник поддержки            | Просмотр обращений своей службы, рабочие переходы статуса, внутренние заметки, поиск исполнителей и назначение |
| `support-lead` | Руководитель поддержки         | Наследует `support`; первоначальный исполнитель новых обращений                                                |
| `admin`        | Администратор службы поддержки | Права поддержки и GET/PUT/PATCH `/api/settings`                                                                |

`support` — логин демонстрационного сотрудника. `support` — техническое имя роли. Это разные значения.

Роли удобно назначать через готовые группы:

| Группа               | Роль клиента `service-desk`       |
| -------------------- | --------------------------------- |
| `desk-customers`     | `customer`                        |
| `desk-support`       | `support`                         |
| `desk-support-leads` | `support-lead`, включая `support` |
| `desk-admins`        | `admin`                           |

Для каждого Service Desk нужен ровно один включённый руководитель с ролью `support-lead`. Новое обращение назначается ему. Если руководителя нет или их несколько, создание возвращает `503` без записи обращения. После создания распределением управляет сервис студентов; при закрытии исполнитель снимается.

## Создание пользователя

1. В консоли Keycloak выбрать realm **training**, затем **Users → Add user**.
2. Указать **Username**, например `sergey.petrov`, имя **Сергей**, фамилию **Петров**. Логин — до 128 символов: латинские буквы, цифры, `.`, `_`, `-`, `@`. Отображаемые имена могут быть русскими. Username затем передаётся в API назначения исполнителя.
3. Задать атрибут **team_slug**. Для текущей общей службы значение — `demo`. Если поле не отображается, администратор проверяет **Realm settings → User profile**: `team_slug` должен быть виден администраторам и доступен им для изменения. В конфигурации стенда он уже описан.
4. Сохранить пользователя. Writable LDAP federation сохранит учётку в LDAP; отдельно создавать LDAP-запись не требуется.
5. В **Credentials → Set password** задать пароль. Для первого входа можно оставить **Temporary = On**, тогда Keycloak предложит смену. Для проверки с заранее выданным постоянным паролем используется **Temporary = Off**.
6. В **Groups → Join group** выбрать одну из групп выше. Например, `desk-support` для сотрудника поддержки.
7. Убедиться, что пользователь включён (**Enabled**). В **Role mapping → Effective roles** проверить итоговые роли клиента `service-desk`, включая наследуемые.

`team_slug` связывает пользователя с существующей службой поддержки. В стенде подготовлена `demo`. Произвольное значение вроде `team-1` в Keycloak само по себе не создаёт новую службу в базе Service Desk: с неподготовленным значением API вернёт `403`.

Прямые назначения и другие группы тоже влияют на эффективные права. Например, удаление `desk-support` не снимет права поддержки, если роль `support` назначена пользователю напрямую.

## Роли вашего приложения

Клиент **student-service** представляет ваше приложение. В нём уже определены роли `user` и `moderator`; их можно использовать как исходную модель:

| Роль `student-service` | Пример назначения в вашем сервисе   |
| ---------------------- | ----------------------------------- |
| `user`                 | Просмотр разрешённых разделов       |
| `moderator`            | Обработка и распределение обращений |

Эти права реализует ваш backend. Service Desk проверяет свои роли клиента `service-desk`.

Пример пользователя, который обрабатывает обращения:

- логин `sergey.petrov`, `team_slug=demo`;
- членство в `desk-support` даёт право вызывать рабочий API Service Desk;
- **Role mapping → Assign role → Filter by clients → student-service → moderator** даёт роль для вашего приложения.

Сначала в **Client scopes → Evaluate** проверить токен выбранного пользователя. Если нужные роли уже выдаются стандартными client scopes, дублирующий mapper не требуется. Если их нет, в **Clients → student-service → Client scopes** открыть dedicated scope клиента и добавить mapper по типу **User Client Role**:

| Поле                | Значение                                |
| ------------------- | --------------------------------------- |
| Client ID           | `student-service`                       |
| Token Claim Name    | `resource_access.student-service.roles` |
| Claim JSON Type     | `String`                                |
| Multivalued         | On                                      |
| Add to access token | On                                      |

Если audience `student-service` ещё нет, в том же scope добавить mapper **Audience**: **Included Client Audience = student-service**, **Add to access token = On**. Собственный backend сможет проверять audience `student-service`. Существующая audience `service-desk` и её mapper сохраняются: они нужны внешнему API.

Названия страниц консоли могут немного различаться между версиями Keycloak. Итог проверяется через **Client scopes → Evaluate** с выбранным пользователем или новым токеном после входа. В текущем шаблоне уже настроены роли и audience Service Desk; наличие определений `student-service:user/moderator` само по себе не гарантирует эти claims в токене.

Ожидаемый фрагмент нового access token после настройки:

```json
{
    "iss": "https://auth.example.ru/realms/training",
    "aud": ["service-desk", "student-service"],
    "preferred_username": "sergey.petrov",
    "name": "Сергей Петров",
    "team_slug": "demo",
    "resource_access": {
        "service-desk": { "roles": ["support"] },
        "student-service": { "roles": ["moderator"] }
    }
}
```

Это пример claims, а не готовый токен. Простое декодирование JWT годится для просмотра; доступ к backend выдаётся только после проверки подписи и остальных ограничений.

## Проверка роли после входа

После назначения роли получить новый токен: выйти и войти снова либо обновить токен через SDK. Уже выданный JWT не переписывается при изменении роли.

С новым access token выполнить:

```http
GET /api/me
Authorization: Bearer <ACCESS_TOKEN>
```

API вернёт `username`, эффективную `role`, русское `roleName` и `teamId`. Для Service Desk приоритет — `admin`, затем `support`, затем `customer`. Руководитель наследует `support`, поэтому серверная эффективная роль может быть `support`.

Для отдельных сценариев использовать отдельные учётки: заявитель, поддержка, руководитель и администратор. Так ошибка выдачи лишних прав не скрывается входом под администратором.

## Типичные причины отказа

| Ситуация                              | Что проверить                                                                    |
| ------------------------------------- | -------------------------------------------------------------------------------- |
| Вход успешен, API отвечает `403`      | Роль именно клиента `service-desk`, активную службу и `team_slug`                |
| В токене нет `moderator`              | Mapper собственного клиента, назначение роли и ограничения role scope            |
| После удаления группы права остались  | Прямые назначения, другие группы и старый токен                                  |
| При создании обращения приходит `503` | Ровно одного включённого руководителя своего Service Desk и доступность каталога |
| Логин `support` не работает           | Демонстрационный логин переименован в `support`; ключ роли остаётся `support`    |
