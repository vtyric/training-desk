# Проверки по области изменения

Проверка выбирается по последствиям изменения. Небольшая правка документа не требует полного SQL-прогона; изменение доступа или доставки не подтверждается одной сборкой. В отчёте указываются фактические команды и результаты.

| Область               | Подходящие проверки                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Документация и skills | `pnpm agents:check`, Prettier изменённых файлов; структура и ссылки, соответствие коду                                               |
| Setup-инструмент      | План без изменений; новые ветки, повторный запуск и ошибки в изолированной копии; сохранность ENV/state; ESLint/Prettier             |
| API, auth и DAL       | `pnpm typecheck`, ESLint, целевые тесты; `pnpm test` при подходящей инфраструктуре                                                   |
| Jira-контракт         | Метод, путь, DTO и коды pinned Data Center snapshot; валидация, роль, принадлежность службе, видимость и пагинация                   |
| JSON настроек         | Полный PUT и частичный PATCH, конкурентные записи/ETag, запрет секретов и произвольных ENV refs, атомарный файл, применение worker   |
| Портал                | Angular typecheck, ESLint/Prettier, `pnpm exec nx run service-desk:build-ui`; загрузка, ошибки и действующий API                     |
| Identity и роли       | Realm/clients/mappers, настоящий Code + PKCE, audience и эффективные роли, отказ без прав, создание пользователя через writable LDAP |
| Тема Identity         | `node tools/build-identity-theme.mjs`, SCSS/assets, рендер FTL на Keycloak; сборка не доказывает внешний вид                         |
| Docker/Compose        | `docker compose config --quiet`, затронутая сборка и запуск с health dependencies через root Compose                                 |

Для отдельной проверки типов доступны:

```sh
pnpm exec tsc --noEmit -p apps/service-desk/tsconfig.server.json
pnpm exec ngc --noEmit -p apps/service-desk/ui/tsconfig.app.json
```

`pnpm build` собирает Service Desk и тему Identity. Проверки не повторяются без новых изменений, ошибок или неразрешённых сомнений. Бюджет CSS и валидация не ослабляются ради успешной сборки.

## Тесты доступа и данных

`pnpm test` использует PostgreSQL разработки. SQL-тесты создают отдельные временные БД и удаляют только их; учётке нужен `CREATEDB`. Перед host-прогоном `pnpm infra:start` открывает dev-порт через override. Обычный root Compose может закрыть его при следующем запуске, не удаляя данные.

JWT-тесты с локальными ключами проверяют подпись и claims, но не доказывают работающий Keycloak/LDAP. Тесты назначения должны проверять актуальные роли из каталога, принадлежность службе, кандидата до первого входа, первоначального руководителя и снятие исполнителя при закрытии. Проверка заявки/history/outbox включает откат при конфликте версии.

Settings-тесты проверяют один JSON-контракт, PATCH вложенных полей, массивы, ETag и защиту от потерянной записи. Проверка callback включает сохранение, SQL-проекцию, смену URL и отключение удалённого получателя без удаления истории.

## Реальные проверки Identity

| Команда                                                                                | Что подтверждает и что меняет                                                                                   |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `pnpm docker:test`                                                                     | LDAP-вход через Keycloak, подписанный Code + PKCE, SSO двух клиентов, создание одного обращения и границу ролей |
| `pnpm swagger:test`                                                                    | Вход клиента Swagger, роли, выход, отказ refresh и silent login после выхода; создаёт обращение                 |
| `pnpm identity:test-users`                                                             | Создание временной LDAP-учётки через Keycloak, пароль и назначение ролей; временная учётка удаляется            |
| `node --env-file=.env tools/identity-smoke.mjs --assignment --close-request --swagger` | Назначение/снятие через живой каталог, закрытие заявителем и роли Swagger; создаёт и закрывает обращение        |
| `node --env-file=.env tools/identity-recovery-smoke.mjs`                               | Конфликт двух вкладок, сохранение state/redirect/PKCE и завершение сессии на локальном Identity                 |

`tests/swagger.test.ts` проверяет OpenAPI, initializer, callback и очистку авторизации. `tests/identity-continuation.test.ts` проверяет доверенный адрес автоматического продолжения, одну попытку и безопасное поведение без browser storage. Эти проверки не заменяют реальный сценарий Identity.

Команды изучаются перед запуском и не направляются на неизвестный удалённый origin. Результат HTTP-проверки и визуальная проверка браузера указываются отдельно. Управление браузером требует согласования.

## Портал и уведомления

Для виртуального списка важны стабильный `issueId` в `trackBy`, одна полоса прокрутки, дозагрузка без потери позиции, отсутствие повторных запросов и игнорирование устаревшего ответа после смены фильтра. AutoResize textarea проверяется также вставкой текста. Сборка подтверждает шаблоны и типы, но не эти визуальные свойства.

Создание обращения не подтверждает webhook. Для доставки нужен включённый публичный HTTPS-получатель и проверка принятого тела/подписи. Тест со stub sender подтверждает обработку состояния доставки, но не сеть. Примеры получателя и локального туннеля находятся в [инструкции интеграции](../students/03-service-desk.md).

## Как описывать результат

Отчёт отделяет форматирование, типы, unit/SQL-тесты, реальный Identity/API-сценарий, доставку webhook и внешний вид. Корневой агент проверяет артефакты и фактический результат сабагентов.

Недоступная БД, Docker, сеть или Identity — ограничение проверки. Она не считается успешным прогоном и не даёт основания заявлять production readiness. ENV, рабочий JSON и основные тома сохраняются при всех проверках.
