# Подготовка локального окружения

Этот документ описывает работу setup-инструментов для агентов. Состав сервисов, порты и постоянные данные находятся в [инструкции Docker](../docker.md). Перед изменением окружения применяется [setup skill](../../.agents/skills/training-desk-setup/SKILL.md).

## План и выполнение

```sh
node tools/bootstrap.mjs --mode docker
node tools/bootstrap.mjs --mode dev
```

Без `--apply` bootstrap только показывает план. Он не создаёт ENV, не устанавливает пакеты и не запускает Docker.

| Режим    | Назначение                                                                |
| -------- | ------------------------------------------------------------------------- |
| `docker` | Готовый локальный стенд: инфраструктура, миграции, Identity, API и портал |
| `dev`    | Инфраструктура в Docker, разработка API/UI на хосте                       |

Согласованная просьба установить или запустить окружение разрешает выбранный запуск с `--apply`. Запрос анализа ограничивается планом.

Prerequisites: Node из `.nvmrc` и диапазона `package.json`, работающий локальный Docker Engine и Compose v2. Для dev также нужна точная версия pnpm из `packageManager`. Глобальные версии, Docker context и lockfile не заменяются для обхода ошибки.

Bootstrap проверяет prerequisites и ENV, запускает общий PostgreSQL, готовит или переносит схему Identity, затем поднимает приложения. В dev он дополнительно устанавливает зависимости с frozen lockfile, применяет миграции и seed. Рабочие API/UI-процессы после этого запускаются через `pnpm start`.

Оба режима вызывают `tools/configure-identity.mjs` после готовности Identity. Это первоначальная настройка профиля/групп и управляемых клиентов, а не постоянно работающий сервис. При ручном запуске Compose её выполняют отдельно через `pnpm identity:configure`.

## Сохранность существующего состояния

`node tools/setup-env.mjs --extend` добавляет отсутствующие ключи и сохраняет действующие секреты. Он также переносит старое имя переменной пароля сотрудника в `LDAP_SUPPORT_PASSWORD` без смены значения. Изменение текста ENV не меняет уже сохранённые пароли LDAP/БД.

`config/backend.json` — шаблон. Рабочий `SETTINGS_FILE` создаётся только при отсутствии; повторный setup его не перезаписывает. Настройки меняет администратор через GET/PUT/PATCH `/api/settings`. Адреса уведомлений применяются без перезапуска, остальные параметры — после него. Секретные значения в JSON не хранятся.

Общая БД `training` содержит `public` и `identity`. Перенос прежнего отдельного Identity PostgreSQL выполняет `tools/migrate-identity-database.mjs`: создаёт резервные копии, останавливает Identity, переносит данные и проверяет результат. Старый том сохраняется. Если перенос не завершён, Identity остаётся остановленным до разбора состояния.

Существующие ENV, JSON и тома не удаляются ради успешного запуска. Конфликт порта решается согласованным адресом и OIDC callback; конфликт миграций — проверкой истории, без редактирования применённого SQL.

## Git hooks

`pnpm hooks:install` подключает версионируемый [pre-commit](../../.githooks/pre-commit) через локальный `core.hooksPath`. Глобальная конфигурация Git не меняется.

Хук запускает только Prettier и ESLint для рабочего дерева. Он не исправляет файлы и не добавляет их в index. Требуются установленные зависимости и Node/pnpm проекта. Ручное форматирование — `pnpm format`; проверка отдельных документов выбирается по [матрице](verification.md).

## Готовность и отчёт

`docker compose ps --all` должен показывать healthy для постоянно работающих сервисов, а `migrate` — завершение с кодом `0`. `/health` подтверждает процесс, но не вход, роли, рендер формы или webhook.

Dev override `infra/compose/dev.yaml` открывает loopback-порты PostgreSQL `55439` и LDAP `1389`. Обычный root Compose может убрать эти публикации при следующем запуске. Фрагменты `infra/compose/*.yaml` используются root aggregator; отдельные приложения запускаются root Compose subsets в общем проекте.

При ошибке фиксируются команда, блокер и сохранённое состояние. Циклические перезапуски, отключение проверок, смена глобального context и удаление данных не являются восстановлением.

Отчёт разделяет подготовку файлов, сборку, готовность сервисов и реальный сценарий входа/доставки. Сквозные проверки создают учебные данные и выполняются только на известном согласованном экземпляре. Управление браузером, публикация, DNS и корпоративная федерация требуют отдельного разрешения.
